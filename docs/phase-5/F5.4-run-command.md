# F5.4 `yaao run` Command

**Phase**: 5 — Execution Engine
**Priority**: Critical
**Dependencies**: F5.1, F5.2, F5.3, F11 (TUI; non-blocking)

## Goal

The end-user entrypoint. Loads a plan, validates, opens the journal, spawns the scheduler+lifecycle pipeline, optionally launches the TUI.

## CLI

```
yaao run <exec-plan> \
  [--max-parallel <n>] \
  [--base-branch <name>] \
  [--dry-run] \
  [--trial] \
  [--no-tui] \
  [--json] \
  [--only <ids>] \
  [--skip <ids>] \
  [--resume <run-id>] \
  [--force]                # required for plan-hash mismatch on resume
```

## Steps

1. Load config (F1.3) and plan (F2.2).
2. Validate (F2.3); abort on errors.
3. Detect agents (F4.7); abort if any used agent is unavailable.
4. If `ctx-sys.enabled`, ensure ctx-sys is reachable (F7.1).
5. Acquire `.yaao/.lock` (file lock); abort if another yaao run is in progress.
6. Open or open-and-resume journal (F3.4).
7. Construct scheduler, run bus, lifecycle worker pool.
8. Launch TUI (F11) on stderr unless `--no-tui` or `--json`.
9. Drive: while not `done()`, take ready tasks, kick off lifecycle workers; await events; on completion, advance the scheduler.
10. On `run:end`, close journal, release lock, exit:
    - 0 if all non-skipped tasks completed.
    - 1 if any task failed.
    - 130 if cancelled by SIGINT.

## Dry Run

`--dry-run` walks the DAG without spawning agents or creating worktrees. It prints (or emits, in `--json`) the planned execution order, the per-task agent assignment, and the parallelism profile per layer.

## Trial Run

`--trial` is shorthand for "execute the plan end-to-end, but as conservatively as possible." It is equivalent to `--max-parallel 1 --no-merge` plus a marker on the journal so the run can be cleaned up easily. Tasks run real agents in real worktrees, in topological order, one at a time; nothing merges back to the base branch. Used to debug a converted plan before committing to a full parallel run.

`--trial` and `--dry-run` are mutually exclusive.

## `--json` mode

Emits NDJSON RunEvents to stdout while the run progresses; equivalent to a programmatic event subscriber. Ideal for CI integration.

## Locking

`.yaao/.lock` is a sentinel file written with `O_EXCL`; contains the running PID and host. On stale lock (process dead), yaao prints a message and the user can `--force-unlock`. Never auto-removes a lock from a live process.

## Acceptance Criteria

- A multi-task plan completes end-to-end against the `FakeBackend` in CI.
- `--dry-run` makes no FS or git mutations.
- `--resume` skips completed tasks and re-runs only incomplete ones.
- Concurrent `yaao run` in the same repo errors with a clear message.
- `--no-tui` produces clean line-oriented logs suitable for piping.
