# F5.1 DAG Scheduler

**Phase**: 5 — Execution Engine
**Priority**: Critical
**Dependencies**: F2.1, F2.3, F3.2

## Goal

Walk the task DAG, surface ready tasks within a parallelism budget, and propagate completions/failures to dependents. Pure logic — no IO, no spawning.

## Status Model

```
pending → ready → active → completed
                       ↘ failed
                       ↘ cancelled
pending → skipped (filtered out by --only/--skip)
pending → skipped (transitive of a failed dep)
```

Transitions are append-only — once `completed`/`failed`/`cancelled`/`skipped`, a task does not re-enter active without an explicit retry (see `task.retries`).

## API

```typescript
// src/exec/scheduler.ts
export interface SchedulerOptions {
  plan: ResolvedPlan;
  filter?: { only?: string[]; skip?: string[] };
  maxParallel: number;
}

export interface Scheduler {
  status(taskId: string): TaskStatus;
  readyTasks(): string[];                    // ids currently ready, capped to maxParallel - active
  startTask(taskId: string): void;           // pending → active
  completeTask(taskId: string, result: TaskOutcome): void;
  failTask(taskId: string, error: YaaoError): void;
  cancelTask(taskId: string, reason: string): void;
  retryTask(taskId: string): void;           // increments attempt count
  done(): boolean;                           // all tasks terminal
  events: AsyncIterable<SchedulerEvent>;
}
```

## Algorithm

- On construction, mark filtered tasks `skipped`. Mark every other task `pending`.
- A pending task becomes `ready` when all its `depends:` are `completed` (or `skipped` when the dep is filtered with `--skip`; see Filter Semantics below).
- `readyTasks()` returns up to `maxParallel - active.size` ready tasks, sorted by:
  1. Number of downstream dependents (more first — keep the critical path saturated).
  2. Lexicographic task ID (deterministic).
- On `failTask`, mark all transitive dependents `skipped` with reason `depFailed`, **unless** the failed task has retries remaining (`task.retries > attempt`), in which case the task is reset to `pending` and `retryTask` is the explicit way to ack that.

## Filter Semantics

- `--only [a,b,c]`: only those tasks (and their dependencies) are eligible; others are skipped.
- `--skip [x,y]`: those tasks are skipped; their dependents are also skipped (with `reason: depFailed`).
- The two flags are mutually exclusive.

## Events

```typescript
export type SchedulerEvent =
  | { type: 'task:queued';    taskId: string; depends: string[] }
  | { type: 'task:ready';     taskId: string }
  | { type: 'task:active';    taskId: string }
  | { type: 'task:completed'; taskId: string; outcome: TaskOutcome }
  | { type: 'task:failed';    taskId: string; error: YaaoError }
  | { type: 'task:skipped';   taskId: string; reason: 'filtered' | 'depFailed' };
```

## Acceptance Criteria

- Pure: no IO, no clock-dependent behavior except via injected `now`.
- Topological correctness verified by comparing against a `Set`-of-completed walk over the validated DAG.
- Parallelism never exceeds `maxParallel` even under bursts of `completeTask`.
- Retries on a failed task put it back in `ready` only when explicitly requested.
- `done()` returns true only when every task is in a terminal state.
