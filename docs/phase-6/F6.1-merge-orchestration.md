# F6.1 Topological Merge Orchestration

**Phase**: 6 — Merge Engine
**Priority**: Critical
**Dependencies**: F3.1, F3.2, F3.3, F5.2

## Goal

After a run finishes, merge the per-task branches back to the base branch in dependency order, surfacing conflicts cleanly and committing only when each merge is clean (or resolved).

## Inputs

```typescript
// src/merge/orchestrator.ts
export interface MergeRequest {
  runId: string;
  plan: ResolvedPlan;
  branchPlan: BranchPlan;          // F3.2
  baseBranch: string;
  rootDir: string;
  policy: MergePolicy;             // global merge policy from config + per-task overrides
}

export interface MergeOutcome {
  merged: string[];                 // task ids successfully merged
  pr: { taskId: string; url: string }[];
  skipped: { taskId: string; reason: string }[];
  conflicts: { taskId: string; files: string[]; mode: 'manual' | 'agent' | 'auto' }[];
  finalCommit: string;              // HEAD of base branch after merge
}

export async function runMerge(req: MergeRequest): Promise<MergeOutcome>;
```

## Algorithm

1. Compute the topological order from the branch plan.
2. Filter to **completed** tasks (failed/skipped/cancelled tasks are excluded).
3. Group by `merge` policy:
   - `none` → recorded in `skipped`, never touched.
   - `pr` → handled in F6.3 (push + PR), no local merge.
   - `auto` / `manual` (default `auto` overall, `manual` on conflict) → merged locally now.
4. Switch to `baseBranch`. For each task in topological order:
   a. Trial merge: `git merge --no-commit --no-ff <task-branch>`.
   b. If clean, commit (`--no-edit`, message generated). Record success.
   c. If conflict:
      - Abort the trial merge (`git merge --abort`).
      - Hand off to F6.2 (`auto`/`manual`/`agent` resolution).
      - On resolution success, commit. On failure, the orchestrator records the conflict and stops merging *further dependent* tasks (their merge would re-trigger the same conflict). Independent tasks continue.
5. After loop, return `MergeOutcome`.

## Why per-task topo merge instead of one big octopus merge?

- Octopus merges fail entirely on a single conflict.
- Per-task merges produce a clean linear-ish history, with one merge commit per task that maps directly to the plan.

## Independent vs Dependent Stopping

If task `B` (which depends on `A`) conflicts and is left unresolved, downstream tasks that depend on `B` are also skipped (re-merge would just re-conflict). Tasks in disjoint subgraphs continue merging.

## Idempotency

`runMerge` is safe to re-invoke on a partially-merged run; it inspects the base branch's commits to detect already-merged task branches (via commit message tags or branch-merged check) and skips them.

## Acceptance Criteria

- A clean diamond DAG produces 3 merge commits (one per task) on the base branch in topo order.
- A conflict on task `B` blocks `B`'s descendants but not other branches.
- Re-running `runMerge` after a resolved conflict completes the remaining merges without re-merging completed ones.
- The function never leaves the base branch in a partial-merge state on any path.
