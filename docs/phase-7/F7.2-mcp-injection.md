# F7.2 MCP Server Registration (ctx-sys + user MCPs)

**Phase**: 7 — ctx-sys Integration (optional)
**Priority**: High
**Dependencies**: F4 (all backends), F7.1, F12.1

## Goal

Make ctx-sys (when enabled) and any user-declared MCP servers visible to whichever agent backend is launched, without permanently editing the user's tool-config files.

This is a **generic** mechanism. ctx-sys is one entry; users can register more in `yaao.config.json`:

```json
"ctx-sys":      { "enabled": true, "auto-spawn": true },
"mcp-servers":  {
  "house-style":    { "command": "npx", "args": ["-y", "@me/style-mcp"] },
  "design-tokens":  { "command": "design-tokens-mcp" }
}
```

When agents spawn, they see yaao's own MCP server (from Phase 12), ctx-sys (when enabled), and every entry under `mcp-servers:`.

## Strategy by Backend

| Backend | How |
|---------|-----|
| `claude-code` | Pass `--mcp-config <tmp.json>` per spawn. |
| `cursor`      | Write managed blocks in `.cursor/mcp.json`, preserving any prior file. Restore on completion. |
| `copilot`     | Write workspace MCP config (path varies by version); restore on completion. |
| `codex`       | TOML overlay via `--config`; never edits `~/.codex/config.toml`. |
| `api`         | Register the MCP servers' tools (via `@modelcontextprotocol/sdk` client) directly into the tool list passed to the model. |

## Combined MCP Config

```typescript
// src/ctx-sys/mcp-config.ts
export interface McpServerConfig {
  name: string;
  command: string;
  args: string[];
  env?: Record<string, string>;
}

export function buildMcpServers(opts: {
  yaaoServer: McpServerConfig;          // from F12.1
  ctxSys?: CtxSysHandle;                // present iff ctx-sys enabled + spawned
  userServers: Record<string, McpServerConfig>;
}): McpServerConfig[];
```

The returned list always includes yaao's own MCP server. ctx-sys is appended when present. User-declared servers are appended last; user-declared names cannot collide with reserved names (`yaao`, `ctx-sys`).

## Restoration Semantics

For backends that overlay a file (cursor, copilot):

- Read the existing file; remember its bytes (or absence).
- Write the new file as a *managed merge*: keep any user MCP servers, add yaao + ctx-sys + user-yaao-declared servers in delimited managed blocks.
- On `AgentProcess` completion (any path — success, fail, cancel), restore the original bytes (or delete the file if it didn't exist).
- Use a write-restore lock (`flock`) so concurrent agent spawns don't collide.

## Concurrency

Multiple agent spawns in the same repo and the same backend do not duplicate the overlay — the lock holder writes once, all spawns share the file, and the last spawn to exit restores. Refcount lives in `.yaao/.mcp-refcount.json`.

## Diagnostics

`yaao doctor` (F13.1) verifies every registered MCP server is reachable from each enabled backend (it spawns a tiny test process per backend that calls the `tools/list` MCP method).

## Acceptance Criteria

- A pre-existing `.cursor/mcp.json` is identical bit-for-bit after a yaao run.
- Concurrent Claude Code and Cursor spawns each see the same set of MCP servers.
- Crash mid-spawn restores the original file (lifecycle's cleanup is `try/finally`).
- API backend exposes `context_query` (when ctx-sys enabled) and yaao's own tools as callable tools to the model.
- User-declared MCP servers appear alongside ctx-sys with the same lifecycle guarantees.
