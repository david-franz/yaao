# F7.2 Per-Agent MCP Config Injection

**Phase**: 7 — ctx-sys Integration
**Priority**: High
**Dependencies**: F4 (all backends), F7.1

## Goal

Make the running ctx-sys MCP server visible to *whichever* agent backend is launched, without permanently editing the user's tool config files.

## Strategy by Backend

| Backend | How |
|---------|-----|
| `claude-code` | Pass `--mcp-config <tmp.json>` per spawn. |
| `cursor`      | Write ephemeral `.cursor/mcp.json`, preserving any prior file. Restore on completion. |
| `copilot`     | Write workspace MCP config (path varies by version); restore on completion. |
| `codex`       | TOML overlay via `--config`; never edits `~/.codex/config.toml`. |
| `api`         | Register the MCP server's tools (via the `@modelcontextprotocol/sdk` client) directly into the tool list passed to the model. |

## Shared MCP Config

```typescript
// src/ctx-sys/mcp-config.ts
export interface McpServerConfig {
  name: 'ctx-sys';
  command: string;
  args: string[];
  env?: Record<string, string>;
}

export function buildCtxSysMcpServer(handle: CtxSysHandle): McpServerConfig;
```

The returned object describes how an MCP client should connect to the running ctx-sys: typically `command: ctx-sys, args: ['client', '--socket', handle.socketPath]` so each agent gets its own short-lived stdio client process that proxies to the long-lived socket server.

## Restoration Semantics

For backends that overlay a file (cursor, copilot):
- Read the existing file; remember its bytes (or absence).
- Write the new file as a *managed merge*: keep any user MCP servers, add `ctx-sys`.
- On `AgentProcess` completion (any path — success, fail, cancel), restore the original bytes (or delete the file if it didn't exist).
- Use a write-restore lock (`flock`) so concurrent agent spawns don't collide.

## Concurrency

Multiple agent spawns in the same repo and the same backend do not duplicate the overlay — the lock holder writes once, all spawns share the file, and the last spawn to exit restores. Refcount lives in `.yaao/.ctx-sys-refcount.json`.

## Diagnostics

`yaao doctor` (F13.1) verifies the MCP server is reachable from each enabled backend (it spawns a tiny test process per backend that calls the `tools/list` MCP method).

## Acceptance Criteria

- A pre-existing `.cursor/mcp.json` is identical bit-for-bit after a yaao run.
- Concurrent Claude Code and Cursor spawns each see the ctx-sys server.
- Crash mid-spawn restores the original file (lifecycle's cleanup is `try/finally`).
- API backend exposes `context_query` as a callable tool to the model.
