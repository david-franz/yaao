# F14.1 `yaao web` HTTP Server

**Phase**: 14 — Web Viewer
**Priority**: High
**Dependencies**: F12.1, F12.5, F12.6, F3.4

## Goal

A local HTTP server that hosts the web viewer and exposes the data it needs over JSON + SSE. Local-only, no auth by default, no external dependencies beyond `npm install -g yaao`.

The web viewer is **observation + management**, not a run launcher. Runs are started from the CLI (`yaao run`) or via the MCP tools (`yaao_run` / `yaao_resume`); the web viewer is what you point your browser at to watch them happen, browse history, edit plans and config, and clean up afterwards.

## Relationship with the MCP server (F12.1)

`yaao serve` and `yaao web` are **separate processes** with different jobs.

- `yaao serve` is the stdio MCP server, spawned by AI clients (Claude Code, Cursor, Copilot, Codex). One process per client, lifetime tied to the client. No human ever runs this from a terminal in normal use.
- `yaao web` is the human-facing HTTP+SSE listener. Spawned from a terminal, points to the project's `cwd`, lifetime tied to the user.
- A single project can have any combination running: zero, one, or several `yaao serve` instances (one per attached AI client) AND a `yaao web` instance.

What they share is **the filesystem**, not in-process state:

```text
  Claude Code              user's terminal
       │                          │
       └─► spawns yaao serve      └─► spawns yaao web
            (stdio MCP)               (HTTP + SSE)
                 │                          │
                 └──────────┬───────────────┘
                            ▼
                 shared .yaao/ directory
                   - .yaao/runs/<id>/journal.jsonl
                   - .yaao/skills/, .yaao/plans/, .yaao/exec/
                   - yaao.config.json
```

Every process runs the F12.6 FS watcher, so changes from any side propagate to all sides without restarts. Concretely:

- A skill the `yaao_distill` MCP tool writes shows up in the web viewer's plan editor within ~250 ms (F12.6 watcher fires; web process re-renders).
- A run Claude Code starts via `yaao_run` writes events to `.yaao/runs/<id>/journal.jsonl`; the web process tails that file via fs.watch and forwards each event over SSE. SSE latency is the journal-flush + FS-watch debounce — sub-second in practice.
- A plan edited in F14.5's in-browser editor is visible to the AI's next `tools/list_changed` (F12.6 fires inside the MCP server process, too).

The journal is the cross-process event channel. F14.1's SSE design — replay via `Last-Event-ID`, tail thereafter — was already built around the journal as the source of truth, so the cross-process case (run started in `yaao serve`, watched in `yaao web`) and the same-process case (run started by `yaao web` if we ever supported it, which we don't) look identical from the browser's perspective.

## CLI

```text
yaao web [--port <n>] [--host 127.0.0.1] [--token <t>] [--no-open]
```

- `--port`: defaults to 0 (kernel-assigned), printed on startup.
- `--host`: defaults to `127.0.0.1`. Non-loopback binds (e.g. `--host 0.0.0.0` to expose the viewer on your LAN) require `--token <t>` — a shared secret clients present as `Authorization: Bearer <t>` or `?token=<t>` for SSE. On the loopback default the token is omitted; anything on `127.0.0.1` is already you.
- `--no-open`: don't auto-launch a browser.

## Stack

- HTTP framework: `hono` (small, fast, ESM, ships well in a CLI).
- Bundled static assets in `dist/web/` produced at build time from `web/` (Phase 14 source).
- Server-Sent Events for live run subscription and live-reload of plans/config.

| GET | `/api/agents` | Output of `yaao agents`. |

### Plans (F14.2, F14.5)

| Method | Path | Purpose |
| --- | --- | --- |

| GET | `/api/plans/:slug/watch` | SSE stream emitting one event whenever the underlying file changes (FS-watch debounced 250 ms). Lets the DAG + editor live-reload. |

### Config (F14.6)

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/config` | The resolved `yaao.config.json` for the project, with `${ENV_VAR}` placeholders preserved (never the resolved literal values). |
| GET | `/api/config/raw` | Raw config JSON. |
| PUT | `/api/config/raw` | Save the edited config. Server runs the Zod parse + secrets-leakage scan; rejects on failure. |
| GET | `/api/config/schema` | The JSON Schema for `yaao.config.json`. Powers the editor's autocomplete. |
| GET | `/api/config/watch` | SSE stream; fires on disk write. |

### Runs (F14.3)

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/runs` | List of runs (latest first). |
| GET | `/api/runs/:runId` | `RunSummary`, identical to `yaao_status`. |
| GET | `/api/runs/:runId/tasks/:id/log?from=<n>` | Captured `output.log` tail since byte offset. |
| GET | `/api/runs/:runId/events` | SSE stream of run events — see "SSE stream" below. |
| POST | `/api/runs/:runId/cancel` | Cancel an in-flight run; idempotent. |
| POST | `/api/runs/:runId/resume` | Same shape as the `yaao_resume` MCP tool. Body: `{ retryFailed?, reskip? }`. |

Run *creation* is deliberately not in the API. Start runs from the CLI or via the `yaao_run` MCP tool; the web viewer watches them, doesn't launch them. Keeping run-start out of the web server simplifies the lifecycle story (the web process doesn't have to own spawning, cancellation propagation across two transports, or auth-on-trigger) and aligns the web viewer with the actual workflow.

## SSE stream — full event coverage

The `task:active` and `task:output`-only spec from the first draft was too narrow — it would show stdout/stderr but drop the events that make watching an agent actually informative (thinking, tool-use, retry attempts, validation outcomes). The HTTP SSE stream now forwards every `RunEvent` the bus emits (F5.2 / [src/exec/bus.ts](../../src/exec/bus.ts)):

| SSE `event` | Payload | Source |
| --- | --- | --- |
| `run:start` | `{ runId, planFile }` | bus `run:start` |
| `run:warning` | `{ runId, message }` | bus `run:warning` (e.g. plan-untracked warn-mode) |
| `run:end` | `{ runId, status }` | bus `run:end` |
| `task:queued` | `{ taskId, depends }` | bus |
| `task:ready` | `{ taskId }` | bus |
| `task:active` | `{ taskId, agent, branch, worktree }` | bus |
| `task:agent-event` | `{ taskId, ev: AgentEvent }` — `ev.type` is `stdout` / `stderr` / `thinking` / `tool-use` | bus |
| `task:diff` | `{ taskId, filesChanged, insertions, deletions }` | bus |
| `task:committed` | `{ taskId, sha }` | bus |
| `task:retry-attempt` | `{ taskId, attempt, error }` | bus |
| `task:completed` | `{ taskId, validation? }` | bus + journal task:completed |
| `task:failed` | `{ taskId, error, validation? }` | bus + journal task:failed |
| `task:skipped` | `{ taskId, reason }` | bus |
| `task:merged` | `{ taskId, into, mergeCommit }` | bus |
| `task:merge-failed` | `{ taskId, into, reason, conflicts }` | bus |

Resume support: clients reconnect with `Last-Event-ID: <n>`; the server replays journaled events since that id from `.yaao/runs/<runId>/journal.jsonl`. Finished runs replay-only.

For `task:agent-event` events, the `ev.data` field (the agent's stdout chunk, thinking block, or serialised tool-use args) is forwarded verbatim. The web client decides how to render — F14.3's "activity stream" is the consumer.

## Auth

- Default: bound to `127.0.0.1`, no token. Anyone on the loopback interface can use it (i.e., the user, intended).
- Non-loopback: a per-server-instance random token must be presented as `Authorization: Bearer <token>` (or `?token=<t>` for SSE). The startup banner prints the URL with the token embedded for convenience.
- All mutating endpoints (`PUT /api/plans/:slug/raw`, `PUT /api/config/raw`, `POST /api/prune`, `POST /api/runs/:runId/cancel`, `POST /api/runs/:runId/resume`) require the token even on loopback when the host is non-loopback. On loopback they're allowed without a token but rate-limited per-IP to ~10/s so a runaway client can't thrash the FS.

## Lifecycle

- The server holds a single project context (cwd at startup). Multi-project is out of scope; users `cd` and re-invoke for a different project.
- `Ctrl-C` shuts down cleanly. SSE clients are tracked; the server emits an `Event: shutdown` then closes each stream before exit.
- `POST /api/runs/:runId/cancel` doesn't terminate the run in-process — the run is happening in a different process (a `yaao serve` an AI client spawned, or a CLI `yaao run`). Instead, the web process writes a cancel marker to `.yaao/runs/<runId>/cancel` and returns 202; the run process polls for it via the same FS watcher the rest of the system uses and stops at the next safe checkpoint. If the run is already finished, the endpoint is a no-op and returns 200.

## Acceptance Criteria

- `yaao web` starts the server and prints a working URL.
- API endpoints return correct shapes; OpenAPI 3.1 spec emitted at `/api/openapi.json`.
- SSE stream survives browser reconnects with no duplicate events (Last-Event-ID replay).
- Non-loopback bind requires a token.
- Run creation is **not** in the API surface; F14.3 has no "start run" affordance.
- `PUT /api/plans/:slug/raw` rejects an invalid plan with structured issues, never writes a broken file.
- `PUT /api/config/raw` rejects a config that has literal secret values, never overwrites placeholders with literals.
