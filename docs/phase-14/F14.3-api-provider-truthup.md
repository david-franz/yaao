# F14.3 API Provider Truth-Up

**Phase**: 14 — Integration Correctness
**Priority**: High
**Dependencies**: F4.6 (API backend), F2.3 (DAG validation)

## Goal

Close two honesty gaps in the API backend:

1. The README promises Anthropic prompt caching. The shipped code doesn't
   set `cache_control` markers anywhere. Either implement caching or
   strip the claim.
2. `OpenAIProvider` and `OpenRouterProvider` are stubs that throw at
   spawn time. Validation should catch the gap before a run starts so
   the user sees the failure mode before any work is committed.

## Scope 1 — Anthropic prompt caching

[src/agents/api/backend.ts AnthropicProvider.step](../../src/agents/api/backend.ts#L238-L319)
builds the request body with `system`, `messages`, and `tools` — no
`cache_control` markers anywhere. Prompt caching is opt-in on
Anthropic's side: you tag a content block with
`{ cache_control: { type: 'ephemeral' } }` to mark a cache breakpoint,
and reads return `cache_creation_input_tokens` /
`cache_read_input_tokens` in the response.

### Recommendation: implement, don't strip

Caching is high-impact for yaao's API backend specifically — the
system prompt, tool definitions, and accumulating conversation
prefix are repeated across every step in the agent's tool-use loop.
Caching the stable prefix saves real money per run, and the implementation
is small.

What to cache, in order of value:

- **System prompt**: stable across every step in a single agent spawn.
  Mark with `cache_control: { type: 'ephemeral' }` on the `system`
  array block.
- **Tool definitions**: same — the tool list is fixed at spawn time.
  Mark the last tool entry's input_schema (the canonical "end of
  tools" cache breakpoint).
- **Prior assistant messages + tool results**: yaao reconstructs the
  conversation each step ([backend.ts:251-275](../../src/agents/api/backend.ts#L251-L275)).
  Mark the most recent `tool_result` block as the next cache
  breakpoint so each step benefits from the previous step's cache.

Anthropic limits prompt caching to 4 breakpoints per request and a
5-minute TTL on `ephemeral`. yaao's pattern (one breakpoint at end of
tools + one at the most recent user/tool-result turn) uses 2 of 4
slots, leaving headroom for future use.

### Telemetry

Surface `cache_creation_input_tokens` and `cache_read_input_tokens`
on each step's `AssistantStep` result, accumulate per spawn, and emit
the totals on `task:completed` so users can see cache hit rate in the
journal + web viewer. Backwards-compatible: existing consumers don't
read the field.

## Scope 2 — Stub providers fail at validate, not spawn

[OpenAIProvider](../../src/agents/api/backend.ts#L337) and
[OpenRouterProvider](../../src/agents/api/backend.ts#L346):

```ts
isAvailable(): { available: boolean; reason?: string } {
  return { available: false, reason: 'openai provider SDK integration is post-MVP' };
}
async step(): Promise<AssistantStep> {
  throw new Error('OpenAIProvider not yet implemented');
}
```

A plan with `agent: api, api: { provider: openai }` survives `yaao
validate` today as long as `OPENAI_API_KEY` is set (validate only
checks for a key, not implementation status). It then crashes at the
first step.

### Change

Add a validation rule to
[src/plan/validate/index.ts](../../src/plan/validate/index.ts) right
after the existing `YAAO_PLAN_API_NO_KEY` check at line 172:

```ts
if (t.agent === 'api' && t.api) {
  const provider = t.api.provider;
  if (provider === 'openai' || provider === 'openrouter') {
    issues.push({
      severity: 'error',
      code: 'YAAO_PLAN_API_PROVIDER_UNIMPLEMENTED',
      message: `task '${t.id}' uses api provider '${provider}' which is not yet implemented`,
      taskId: t.id,
      location: source.get(t.id),
      hint: 'use provider: anthropic, or wait for the openai/openrouter implementation',
    });
  }
}
```

The error has the same shape as `YAAO_PLAN_AGENT_DISABLED` (which
F14.1 makes a hard-stop on run) so the run-time gate from F14.1
catches it without further plumbing.

## Acceptance criteria

### Anthropic caching

- A test spawn with the AnthropicProvider verifies the request body
  has `cache_control: { type: 'ephemeral' }` on:
  - the last block of the `system` array
  - the last `input_schema` in the `tools` array
  - the most recent `tool_result` block in `messages`
- Multi-step spawns (3+ tool-use rounds) record nonzero
  `cache_read_input_tokens` in step 2+ (asserted against a recorded
  Anthropic fixture).
- `task:completed` event payload includes
  `apiCache: { creation: N, reads: M }` when the backend is `api` and
  the provider is `anthropic`.

### Stub provider validation

- `yaao validate` on a plan with `provider: openai` returns
  `YAAO_PLAN_API_PROVIDER_UNIMPLEMENTED` (error severity).
- Same for `openrouter`.
- `yaao run` on the same plan refuses to start (gated by F14.1's
  validate-on-run).
- Existing `provider: anthropic` plans pass validation unchanged.
- The README's "Backend support tiers" table is updated:
  Anthropic moves from "stubs" hedge to fully shipped; OpenAI and
  OpenRouter are explicitly marked "validate-time error until shipped"
  rather than "stubs."

## Out of scope

- **Building working OpenAI / OpenRouter providers.** F14.3 makes the
  failure mode visible at validate time. The actual provider
  implementations are deferred (likely between Phases 17 and 18).
- **A general "provider capability" surface** beyond the single
  validation rule. If we ever ship Bedrock, Vertex, etc., each gets
  its own row in the `isAvailable` check + validate rule.
- **Cache control on the user prompt itself.** The user prompt is
  task-specific and unlikely to repeat; caching it costs more than
  it saves. The three breakpoints above are the right scope.
