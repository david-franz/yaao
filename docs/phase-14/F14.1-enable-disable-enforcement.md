# F14.1 Enable-Disable Enforcement End-to-End

**Phase**: 14 — Integration Correctness
**Priority**: Critical (closes the user-visible bug)
**Dependencies**: F1.3 (config schema), F2.3 (DAG validation), F5.4 (run command)

## Goal

Make `agents.<name>.enabled: false` actually disable the agent across every
yaao surface — planner suggestions, converter assignment, validate, run
(CLI), and `yaao_run` (MCP). Today a user who disables `claude-code` can
still have claude-code agents spawned by `yaao run`, because three layers
of the pipeline ignore the toggle.

## The failure chain (observed)

A user opened a fresh project with `claude-code.enabled: false`,
`copilot.enabled: true`, `defaults.agent: 'claude-code'` (the schema
default). Ran `yaao plan` and `yaao run`. Claude-code agents spawned
anyway. Three causes stacked:

1. [src/cli/commands/plan.ts:42](../../src/cli/commands/plan.ts#L42) —
   `agentName = flags.agent ?? ctx.config.defaults.agent`. No `enabled`
   check; the planner runs Claude Code as long as the binary is on PATH.
2. [src/skills/builtin/yaao-planner/skill.yaml](../../src/skills/builtin/yaao-planner/skill.yaml) —
   no `enabled-agents` input. The prompt's worked-example task table at
   [prompt.md:70-74](../../src/skills/builtin/yaao-planner/prompt.md#L70-L74)
   hard-codes `claude-code` for 3/5 sample tasks, so the model
   pattern-matches it into the generated plan.
3. [src/cli/commands/run.ts:71-194](../../src/cli/commands/run.ts#L71) —
   `loadPlan` → `runPlan` with no `validatePlan` call.
   [run.ts:212 backendForTask](../../src/cli/commands/run.ts#L212) is a
   bare `switch(task.agent)`. The existing `YAAO_PLAN_AGENT_DISABLED`
   validation error at [validate/index.ts:150](../../src/plan/validate/index.ts#L150)
   is dead code in the normal flow.
4. Even the converter — which DOES check `enabled` via
   [assign-agent.ts:128 `finalizeEnabledFallback`](../../src/converter/assign-agent.ts#L128) —
   demotes to `config.defaults.agent`. With `defaults.agent: claude-code`
   and `claude-code.enabled: false`, the fallback is itself the disabled
   agent. Endless demotion to the same thing.

## Design

### Change 1 — runtime gate in `yaao run` and `yaao_run`

Add a pre-flight validation pass to [src/cli/commands/run.ts](../../src/cli/commands/run.ts)
and [src/mcp/tools.ts](../../src/mcp/tools.ts) (`yaao_run` handler) that
calls `validatePlan(plan, source, { config })` and stops on any error.
Specifically blocks `YAAO_PLAN_AGENT_DISABLED`, `YAAO_PLAN_API_NO_KEY`,
and (new in F14.3) `YAAO_PLAN_API_PROVIDER_UNIMPLEMENTED`.

Add a `--allow-disabled-agents` CLI flag (and matching MCP option) that
downgrades the disabled-agent error to a warning for emergencies. The
default is hard-stop.

### Change 2 — defense-in-depth at backend dispatch

[src/cli/commands/run.ts:212 backendForTask](../../src/cli/commands/run.ts#L212)
and [src/mcp/tools.ts:1307 defaultBackendFor](../../src/mcp/tools.ts#L1307)
both check `agents.<name>.enabled` before constructing the backend. On
`enabled: false`, throw a new `AgentDisabledError` with
`code: YAAO_AGENT_DISABLED` (distinct from `YAAO_PLAN_AGENT_DISABLED`,
which is the validate-time variant). The error references the same
config key in its `hint:` so the user knows the exact path to fix.

This catches the case where someone disables the validation gate via
`--allow-disabled-agents` but the backend can't actually run, and the
case where a programmatic caller skips validation entirely.

### Change 3 — planner skill is config-aware

Add a fifth input to [src/skills/builtin/yaao-planner/skill.yaml](../../src/skills/builtin/yaao-planner/skill.yaml):

```yaml
inputs:
  - name: enabled-agents
    description: Comma-separated list of agents the user has enabled in yaao.config.json
    required: true
```

[src/planner/run.ts:126-135](../../src/planner/run.ts#L126-L135)
computes the value from `opts.config` (using the same `enabledAgents`
helper as [skills/install.ts:136](../../src/skills/install.ts#L136)) and
passes it through `substitutePlaceholders`.

The prompt body changes:

- The introduction adds: "You MAY only suggest agents from this list:
  `{{enabled-agents}}`. Tasks assigned to any other agent will be
  rejected at validation time."
- The worked-example table is rewritten to use a templated placeholder
  per task rather than hard-coded `claude-code`. Something like
  `<the most appropriate agent from {{enabled-agents}}>` so the model
  reads the list and picks from it.

### Change 4 — converter fallback is config-aware

[src/converter/assign-agent.ts:128 `finalizeEnabledFallback`](../../src/converter/assign-agent.ts#L128)
currently demotes to `config.defaults.agent` blindly. Replace with: walk
the agent list in `defaults` → `enabled order` (claude-code, cursor,
copilot, codex, api) and pick the first one that's `enabled !== false`
AND has resolvable credentials (for `api`). If none qualify, throw a
new `YAAO_NO_ENABLED_AGENTS` error with a hint pointing at
`yaao.config.json` and `yaao doctor` (when Phase 15 ships).

Same change in `assignAgent` step 3 (project default fallback,
[assign-agent.ts:85-92](../../src/converter/assign-agent.ts#L85-L92)).

### Change 5 — `yaao plan` resolves a sensible backend

[src/cli/commands/plan.ts:42](../../src/cli/commands/plan.ts#L42) and
[backendFor](../../src/cli/commands/plan.ts#L90) need the same fallback
walk as Change 4. If `--agent` is passed explicitly, honor it (and fail
loudly if it's disabled). Otherwise pick the first enabled CLI agent.

## Acceptance criteria

- A plan with `agent: claude-code` and `agents.claude-code.enabled: false`
  in config: `yaao run` exits non-zero with `YAAO_PLAN_AGENT_DISABLED`
  and never spawns any backend.
- `yaao_run` over MCP returns the same error in its response envelope;
  no agent process is created.
- `yaao plan` invoked with `defaults.agent: claude-code` and
  `claude-code.enabled: false` AND `copilot.enabled: true` uses
  copilot as the planner backend.
- The planner skill prompt, when rendered with
  `enabled-agents: copilot`, contains no hard-coded `claude-code` in
  the worked example.
- The converter's `assignAgent` fallback, with `claude-code` disabled
  and `defaults.agent: claude-code`, picks the next enabled CLI agent
  rather than producing a self-disabled assignment.
- With every agent disabled and no `api.providers`, both the planner
  and the converter raise `YAAO_NO_ENABLED_AGENTS` with a hint pointing
  at `yaao.config.json`.
- `--allow-disabled-agents` downgrades the run-time gate to a warning
  but does NOT bypass the backend-dispatch guard (the spawn still
  refuses; that's intentional defense-in-depth).

  with the flag, validation is a warning; spawn-time guard still
  refuses.

## Out of scope

- **Removing `defaults.agent: claude-code` from the schema's default.**
  Long-standing default; changing it would break every existing
  config. F14.1 makes the default robust instead.
- **A `yaao config doctor`-style "are my enabled agents sane?" check.**
  Phase 15's `yaao doctor` (formerly F14.1) covers this surface.
- **Streaming the enabled-agents list into the converter skill too.**
  The converter skill is invoked as a CLI tool, not driven by a chat
  agent; its assignment logic lives in TypeScript ([assign-agent.ts](../../src/converter/assign-agent.ts))
  and that's what Change 4 updates. The skill prompt is unchanged.
