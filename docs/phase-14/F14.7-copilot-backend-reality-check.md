# F14.7 Copilot Backend Reality Check + Working Implementation

**Phase**: 14 — Integration Correctness
**Priority**: High (gates the "all five integrations work" promise)
**Dependencies**: F4.4 (Copilot backend scaffold), F14.4 (live smoke tests)

## Goal

Ship a Copilot backend that actually works against the current
`gh-copilot` extension. Today [src/agents/copilot.ts](../../src/agents/copilot.ts)
calls `gh copilot agent run` with the prompt on stdin, but it's unclear
whether that subcommand exists in the shipped `gh-copilot` extension or
whether the agentic surface lives somewhere else entirely. F14.4's live
smoke tests will surface the gap; F14.7 is the work to close it.

This is the only one of the five integrations where the shape of the fix
isn't certain at planning time. The phase opens with a research step,
then commits to one of three documented pivot paths.

## Stage 1 — Discovery

Run the current `gh-copilot` extension and verify:

- `gh extension install github/gh-copilot` — does this still install the
  agentic extension, or has GitHub renamed/restructured it?
- `gh copilot --help` — what subcommands actually exist? Today
  `suggest` and `explain` are the documented surface (shell-command
  suggestions and code explanation). Is there an `agent`, `agent run`,
  or similar?
- If an agentic command exists: what's the exact flag/stdin shape, what
  does its output look like (plain text, JSON-line stream, structured
  blocks), does it accept MCP config via a file path or env var?
- If no agentic command exists: is there a different binary entirely
  (e.g. `copilot-cli`) that GitHub ships for agentic use? Are there
  preview / beta flags? Is there a published REST API surface for
  Copilot Chat that yaao should use instead of a CLI?

Output: a short status doc (committed to the phase docs) listing what
exists, what's missing, and which Stage 2 path applies.

### Stage 1 side-quest — fix misleading version reporting

Independent of which Stage 2 path lands, the existing
[CopilotBackend.isAvailable](../../src/agents/copilot.ts#L29-L52)
reports the `gh` binary's version, not Copilot's. A user with `gh`
installed but the gh-copilot extension absent sees `✔ copilot v2.88.1`
in `yaao agents` — the row is green and the version is correct, but
the version is for `gh` itself, not Copilot. Misleading.

Fix as part of Stage 1's audit: probe for the extension specifically
(e.g. `gh copilot --version` or `gh extension list | grep gh-copilot`)
and report Copilot's version, or mark unavailable when the extension
isn't installed even if `gh` is. The version-reporting fix lands
regardless of Stage 2 outcome.

## Stage 2 — Commit to one of three paths

### Path A — `gh copilot` has an agentic command

Most-hoped-for outcome. Update [src/agents/copilot.ts](../../src/agents/copilot.ts):

- Replace `buildCopilotArgs` to match the real command shape.
- Add the right output parser (likely a JSON-line parser if Copilot
  emits structured events, mirroring [parseCodexJsonLine](../../src/agents/codex.ts#L29)
  for Codex).
- Implement [F14.2](F14.2-per-spawn-mcp-overlays.md)'s per-spawn MCP
  overlay using whatever config mechanism Copilot accepts.
- Keep the existing `gh auth status` pre-flight in
  [isAvailable](../../src/agents/copilot.ts#L29-L52).

### Path B — Use Copilot Chat via REST

If there's no agentic CLI but Copilot Chat exposes a REST API the user's
`gh auth` token can hit:

- Add a `CopilotProvider` to the API backend's provider list
  ([src/agents/api/](../../src/agents/api/)) alongside Anthropic, OpenAI,
  OpenRouter. The provider implements `ApiProvider.step` against
  GitHub's Copilot Chat endpoint, using the `gh auth token` for
  authentication.
- Update [src/agents/copilot.ts](../../src/agents/copilot.ts): when the
  CLI agentic command is absent, the `CopilotBackend.spawn` path
  delegates to an in-process API run using `CopilotProvider`. From the
  user's perspective they still write `agent: copilot` in their plan;
  the implementation under the hood is the API loop.
- The `gh auth status` pre-flight stays as the availability probe (no
  separate API-key handling — the GitHub CLI's token is reused).
- This path preserves the `agent: copilot` user-facing identifier so
  existing plans don't have to change shape.

### Path C — Copilot is unsupportable today

If neither CLI nor REST is available, the honest move is to ship
documentation rather than broken integration:

- [src/agents/copilot.ts](../../src/agents/copilot.ts) `isAvailable`
  returns `{ available: false, reason: 'github copilot agentic CLI is
  not available; see docs/phase-14/F14.7 for status' }`.
- A new validation rule `YAAO_PLAN_AGENT_UNSUPPORTED_TODAY` for
  `agent: copilot` plans, parallel to F14.3's
  `YAAO_PLAN_API_PROVIDER_UNIMPLEMENTED`. The error lists which
  alternatives the user has (`claude-code`, `cursor`, `codex`,
  `api/anthropic`, `api/openai`, `api/openrouter`).
- README updates: Copilot moves from "Tier 3 best-effort" to
  "Not available in v1; see [F14.7](docs/phase-14/F14.7-copilot-backend-reality-check.md)
  for status." Honest about the gap rather than carrying a broken
  promise into v1.

If Path C is the outcome, F14.7 explicitly does **not** block Phase 14
shipment. The phase's promise becomes "all four available integrations
work confidently; Copilot is a documented v2 deferral" and the README
matches.

## Acceptance criteria

### Path A acceptance

- A live smoke test (`tests/phase-14/live/copilot-live.test.ts`,
  introduced in F14.4) spawns Copilot against a trivial prompt and
  succeeds.
- The backend's output parser produces structured `AgentEvent`s
  matching Copilot's actual output shape.
- F14.2's per-spawn MCP overlay reaches Copilot (verified by an
  integration test).
- The README's "Backend support tiers" table moves Copilot from
  "Tier 3 best-effort" to "Tier 2 smoke-tested per release" (or
  Tier 1 if the surface is stable).

### Path B acceptance

- A `CopilotProvider` exists in `src/agents/api/`.
- `agent: copilot` plans run via the API loop without the user noticing
  the implementation pivot.
- Live test exercises the REST round-trip with a `gh auth` token.

### Path C acceptance

- `agent: copilot` plans raise
  `YAAO_PLAN_AGENT_UNSUPPORTED_TODAY` at validation.
- The README is updated to call this out explicitly under the existing
  Backend support tiers table.
- A `docs/phase-14/F14.7-copilot-status.md` (or extension of this doc)
  records the Stage 1 findings so a future contributor can pick up the
  work when the upstream surface stabilizes.

## Out of scope

- **A second Copilot integration path** (e.g. shipping both Path A and
  Path B). Pick one based on Stage 1; the other lands as v2 work if
  needed.
- **GitHub Copilot Workspace integration.** A separate product surface
  from Copilot Chat / agentic CLI. Out of scope for v1.
- **Auth flows other than `gh auth`.** F14.7 reuses whatever `gh` has
  already authenticated; no separate `COPILOT_API_KEY` env var.
- **Implementing Path C and then later upgrading to Path A.** Future
  work — yaao's backend interface makes the swap cheap once the
  upstream surface is ready.
