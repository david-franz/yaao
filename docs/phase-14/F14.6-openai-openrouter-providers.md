# F14.6 OpenAI + OpenRouter Provider Implementations

**Phase**: 14 — Integration Correctness
**Priority**: High
**Dependencies**: F4.6 (API backend scaffold), F14.3 (validation truth-up)

## Goal

Ship working `OpenAIProvider` and `OpenRouterProvider` so that
`agent: api` with `provider: openai` or `provider: openrouter` runs
end-to-end with the tool-use loop the AnthropicProvider already supports.
After this lands, every documented provider in the API backend works for
real — F14.3's `YAAO_PLAN_API_PROVIDER_UNIMPLEMENTED` validation rule
becomes unreachable and is removed in the same PR.

## Design

### OpenAIProvider

Implements `ApiProvider.step` against OpenAI's chat completions endpoint
(`POST /v1/chat/completions`) with tool-use enabled. Mirrors the
AnthropicProvider's stateless, request-driven design: apiKey and baseUrl
come from `req.apiKey` / `req.baseUrl` per call, no provider-level
state.

**Conversation reconstruction** ([AnthropicProvider:251-275](../../src/agents/api/backend.ts#L251-L275)
is the reference):

```ts
const messages: OpenAIMessage[] = [
  { role: 'system', content: req.systemPrompt },
  { role: 'user', content: req.prompt },
];
for (const prev of req.prevAssistantMessages ?? []) {
  // OpenAI's "assistant with tool_calls" + "tool results as role: 'tool'" shape
  messages.push({
    role: 'assistant',
    content: prev.text || null,
    ...(prev.toolCalls.length > 0
      ? { tool_calls: prev.toolCalls.map(tc => ({
          id: tc.id,
          type: 'function',
          function: { name: tc.name, arguments: JSON.stringify(tc.input) },
        })) }
      : {}),
  });
  for (const tr of prev.toolResults ?? []) {
    messages.push({
      role: 'tool',
      tool_call_id: tr.id,
      content: tr.content,
    });
  }
}
```

**Tools** translated from yaao's `ApiToolDefinition` to OpenAI's
`{ type: 'function', function: { name, description, parameters } }`
shape.

**Response parsing** — `choices[0].message`:

- `content` (string | null) → `AssistantStep.text`
- `tool_calls: [{ id, type: 'function', function: { name, arguments: <JSON string> } }]`
  → `ApiToolCall[]` (parse `arguments` back into structured input)
- `finish_reason` — `tool_calls` means there are more turns, anything
  else means stop.

**Errors**: surface the OpenAI error body's `error.message` field (or
the first 500 chars of the response body) in the thrown Error, mirroring
the Anthropic provider's diagnostic.

**Telemetry / caching**: OpenAI introduced automatic prompt caching for
prefixes ≥ 1024 tokens — no `cache_control` markers needed. The response
exposes `usage.prompt_tokens_details.cached_tokens`. Surface this on
each `AssistantStep` (new optional field) and accumulate into
`task:completed` payload the same way F14.3 wires Anthropic's
`cache_read_input_tokens`.

### OpenRouterProvider

OpenRouter exposes an OpenAI-compatible chat completions API at
`https://openrouter.ai/api/v1/chat/completions`. The provider is
essentially `OpenAIProvider` with a different default `baseUrl` and a
note about the model namespace (`anthropic/claude-3.5-sonnet`,
`openai/gpt-4`, etc.).

Implementation choice: factor the shared OpenAI-compatible logic into a
helper (`stepOpenAICompatible(req, opts)`) that both providers call.
OpenRouter sets a different default `baseUrl` and may set
`HTTP-Referer` / `X-Title` headers that OpenRouter's API expects for
attribution.

**Model namespace**: OpenRouter's identifiers include a vendor prefix.
Document this in the OpenRouter provider's header comment so a user
writing `model: claude-3.5-sonnet` against OpenRouter doesn't waste a
debugging session — the error from OpenRouter is clear if the model is
unknown, but pre-flight wisdom is cheap.

**Telemetry**: OpenRouter doesn't surface cache details uniformly across
the models it proxies. Skip cache telemetry for OpenRouter; document
that the `apiCache` field on `task:completed` is provider-dependent.

### Config schema

[src/config/schema.ts](../../src/config/schema.ts) — verify the
`agents.api.providers` shape accepts `openai` and `openrouter` entries
with `api-key` and (for OpenRouter) optional `base-url`. The existing
schema is permissive enough (a record of provider names) but the
shipped default config under [src/init/scaffold.ts](../../src/init/scaffold.ts)
should add openai and openrouter entries (commented or empty) so users
discover them by inspection.

## Acceptance criteria

- A plan with `agent: api, api: { provider: openai, model: 'gpt-4o-mini' }`
  validates cleanly when `OPENAI_API_KEY` resolves.
- A plan with `agent: api, api: { provider: openai }` and no resolvable
  key still raises `YAAO_PLAN_API_NO_KEY` (existing rule).
- The same shape works for `provider: openrouter` against
  `https://openrouter.ai/api/v1`.
- A small fixture spawn against OpenAI's `gpt-4o-mini`: one tool call
  (`read_file`) succeeds, the agent receives the tool result, produces
  a final assistant message, exits cleanly.
- The same fixture works against OpenRouter using a model identifier
  with the OpenRouter vendor prefix.
- F14.3's `YAAO_PLAN_API_PROVIDER_UNIMPLEMENTED` is removed; tests that
  asserted it now assert the success path.
- `task:completed` for an openai spawn includes
  `apiCache: { cached: N }` reflecting the `cached_tokens` value
  reported in the response.

## Out of scope

- **Streaming.** All three providers (Anthropic, OpenAI, OpenRouter)
  use the non-streaming completion shape today. Switching to SSE
  streaming is a future cleanup — yaao's tool-use loop is round-trip
  based anyway, so streaming saves wall-clock only on the final
  assistant turn.
- **Per-provider model alias maps** (like
  [resolveClaudeModel](../../src/agents/claude-code.ts#L18) does for
  Claude). Users pass the canonical model id (`gpt-4o`, not a shorthand);
  add aliases later if real users request them.
- **Vision / image input.** Tools-only for v1. The
  `ApiToolDefinition.inputSchema` already supports arbitrary JSON, but
  the user prompt path is string-only.
- **OpenAI Responses API.** The newer `/v1/responses` endpoint has
  better cache semantics but the chat-completions endpoint is stable
  and widely supported. Migration is a v2 candidate.
- **Anthropic Bedrock / Vertex.** Additional Anthropic deployments are
  separate providers; not in scope for v1.
