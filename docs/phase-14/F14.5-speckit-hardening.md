# F14.5 Spec Kit Parser Hardening + Content Propagation

**Phase**: 14 — Integration Correctness
**Priority**: Medium
**Dependencies**: F9.3 (Spec Kit emit), F10.3 (Spec Kit parse)

## Goal

Make the Spec Kit integration handle real-world inputs and not drop
content silently. Today the parser succeeds only on yaao's own emitted
shape; a slightly-off `tasks.md` parses as **zero tasks with no
warning**, and `spec.md` / `plan.md` content is dropped after title +
description extraction.

This matters for two real scenarios: a user authoring Spec Kit triplets
in upstream `specify` (different conventions than yaao's), and a user
who put architectural context in `plan.md` expecting it to flow through
to the execution plan.

## The two gaps

### Gap 1 — strict parser silently emits zero tasks

[src/planner/speckit.ts:39](../../src/planner/speckit.ts#L39):

```ts
const TASK_LINE_RE = /^-\s*\[[xX ]\]\s*\*\*([a-z][a-z0-9-_]*)\*\*\s*[—-]\s*(.+)$/;
```

The regex requires:

- Exactly `- [ ]` or `- [x]` checkbox (no `- [X]`-with-space variant
  beyond the included set, no missing checkbox).
- Bold via **double** asterisks (`**id**`). Single asterisks fail.
- Em-dash (`—`) or ASCII hyphen-minus (`-`). En-dash (`–`) fails.
- Lowercase-only task id.

A `tasks.md` that uses *id* (single asterisks), or `- id - title`
(no checkbox), or any of these variants parses as **zero tasks** and
the rest of the pipeline (`yaao convert`) just produces an empty
execution plan. No warning is issued.

The user sees `yaao convert` succeed silently, `yaao run` says "0
tasks queued," and they have to read source to figure out what
happened.

### Gap 2 — spec.md / plan.md content is dropped

[src/planner/speckit.ts:49-50](../../src/planner/speckit.ts#L49-L50):

```ts
out.title = triplet.title ?? extractTitle(triplet.spec ?? triplet.plan ?? triplet.tasks);
out.description = extractDescription(triplet.spec ?? triplet.plan ?? '');
```

Only the title (first `# ` line) and a one-line description (first
non-empty line after the title) are read from `spec.md`. `plan.md`
contributes nothing if `spec.md` exists. Both files are otherwise
discarded.

A user who wrote architectural decisions in `plan.md`
("we chose Postgres because…", "the auth layer uses…") expects that
context to inform the per-task agents. It doesn't.

## Design

### Change 1 — surface "zero tasks parsed" as a warning

[src/planner/speckit.ts:53-89](../../src/planner/speckit.ts#L53-L89)
already populates `out.issues`. Add:

```ts
if (out.tasks.length === 0) {
  out.issues.push({
    code: 'YAAO_SPECKIT_PARSE_EMPTY',
    message: 'tasks.md produced zero tasks — the task-line shape did not match.',
  });
  out.issues.push({
    code: 'YAAO_SPECKIT_PARSE_HINT',
    message: 'tasks.md task lines must match: `- [ ] **task-id** — Title`. Check checkbox, bold asterisks, em-dash.',
  });
}
```

[src/cli/commands/convert.ts](../../src/cli/commands/convert.ts) and
the converter MCP tool surface these issues to the user (already
plumbed in the converter's `result.issues` propagation, but verify
the path is wired end-to-end).

### Change 2 — relax common variants

Make the regex more forgiving without losing precision:

```ts
const TASK_LINE_RE = /^[-*]\s*(?:\[[xX ]\]\s*)?(?:\*\*|__|\*|_)([a-z][a-z0-9-_]*)(?:\*\*|__|\*|_)\s*[—–-]\s*(.+)$/;
```

This accepts:
- `-` or `*` bullet markers.
- Optional checkbox (so plans authored without it still parse).
- `**id**`, `__id__`, `*id*`, or `_id_` for emphasis.
- `—`, `–`, or `-` separators.

Anything that doesn't match still produces `YAAO_SPECKIT_PARSE_EMPTY`.
The relaxation is bounded; we don't accept arbitrary `- thing -
title` (no emphasis at all) because we'd start grabbing prose lines as
tasks.

### Change 3 — propagate spec.md and plan.md content

Two options:

**Option A (minimal)**: extend `ParsedPlan` with two new optional
fields:

```ts
export interface ParsedPlan {
  // ... existing
  specContent?: string;
  planContent?: string;
}
```

`parseSpecKit` populates them with the full body of each file. The
converter ([src/converter/convert.ts](../../src/converter/convert.ts))
threads `specContent` and `planContent` into the generated execution
plan's `plan.description` field (or a new `plan.context` field — see
schema decision below).

**Option B (recommended)**: add a `plan.context` field to the
execution-plan schema ([src/plan/schema/plan.ts](../../src/plan/schema/plan.ts)):

```yaml
plan:
  name: my-feature
  context: |
    From spec.md:
    <spec body>

    From plan.md:
    <plan body>
```

This content is included verbatim in each task's prompt prefix at
lifecycle time (similar to Phase 16 F16.3's context.md handoff, but
plan-scoped rather than task-scoped). Token-budgeted under
`config.context.plan-context-budget` (default 4000 tokens).

Option B is the right scope: the context belongs at plan level, not
overloaded onto `description`.

### Change 4 — document the shape

Add a `docs/spec-kit-format.md` (or extend the existing planner skill
doc) with:
- The exact `tasks.md` task-line shape the parser accepts.
- The list of relaxed variants from Change 2.
- A note that `spec.md` and `plan.md` bodies are propagated through
  to per-task prompts via `plan.context`.

## Acceptance criteria

- A `tasks.md` with no parseable tasks produces `YAAO_SPECKIT_PARSE_EMPTY`
  + a hint. `yaao convert` surfaces it as a warning (or error in
  strict mode).
- Each of these variants parses as a valid task:
  - `- [ ] **task-id** — Title`
  - `- [x] **task-id** — Title` (already worked)
  - `* [ ] **task-id** — Title`
  - `- **task-id** — Title` (no checkbox)
  - `- [ ] *task-id* — Title` (single asterisks)
  - `- [ ] **task-id** – Title` (en-dash)
- The malformed shape `- task-id - Title` (no emphasis) still
  produces zero tasks (we don't grab prose lines).
- A converted plan from a Spec Kit triplet containing non-trivial
  `spec.md` and `plan.md` has a `plan.context` field with both bodies
  included.
- Per-task prompts at run time include the `plan.context` content
  (capped by the budget). Existing prompt-prefix paths still work.
- Existing tests under `tests/phase-10/` continue to pass without
  modification.

## Out of scope

- **Generic markdown task-list parsing.** The yaao Spec Kit task-line
  shape is documented; we relax the most common variants and stop
  there. Full CommonMark task-list support would require a real
  parser and is overkill.
- **Round-trip preservation of arbitrary `tasks.md` formatting.** The
  parser is read-only; `serializeSpecKit` writes the canonical shape.
  Users who author by hand and want their formatting preserved on
  round trip should track the file in git.
- **Schema validation of `plan.context` content.** It's an opaque
  string; the agents decide what to do with it.
- **Inlining `spec.md` into every task by default.** Users who don't
  want plan-level context propagated can omit `spec.md` and `plan.md`
  from their triplet, or set `config.context.plan-context-budget: 0`.
