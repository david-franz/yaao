# F14.9 Base-Branch Detection + `--feature-branch` CLI Plumbing

**Phase**: 14 — Integration Correctness
**Priority**: High (silently bricks every master-default repo today)
**Dependencies**: F1.4 (init), F2.1 (plan schema), F3.3 (git wrapper), F5.4 (run command)

## Goal

Close two related "what branch is this run targeting?" defects:

1. **Base-branch is hard-coded to `main`** through the whole stack —
   schema, init scaffold, plan resolution, branch policy. A repo using
   `master` only fails at worktree creation with a cryptic
   `git rev-parse --verify` error. Every sufficiently old GitHub repo
   hits this on first `yaao run`.
2. **`--feature-branch` (and `--base-branch`) CLI flags aren't plumbed
   uniformly across plan/convert/run.** The MCP equivalents already
   work — `yaao_convert` takes a `featureBranch` argument that lands
   verbatim in the generated YAML
   ([tools.ts:162-175](../../src/mcp/tools.ts#L162-L175)), and `yaao_run`
   takes a runtime `featureBranch` override
   ([tools.ts:273-298](../../src/mcp/tools.ts#L273-L298)). Only the
   CLI surface is missing the flags.

## Current state (as of the audit)

### Base-branch handling

- **Schema default** ([schema.ts:20](../../src/config/schema.ts#L20)):
  `'base-branch': z.string().default('main')`. Hard-coded.
- **Init scaffold** ([scaffold.ts:22](../../src/init/scaffold.ts#L22)):
  `buildDefaultConfigJson()` writes `'base-branch': 'main'`
  unconditionally. `yaao init` makes zero git calls to detect the repo's
  actual default branch.
- **Plan resolution** ([resolve.ts:69](../../src/plan/schema/resolve.ts#L69)):
  `baseBranch = planCfg['base-branch'] ?? cfg.defaults['base-branch']`.
  Falls back to whatever the config holds. No existence check.
- **Runtime failure** ([worktree-manager.ts:132](../../src/git/worktree-manager.ts#L132)):
  `await this.git.revParse(req.baseBranch, req.rootDir)` throws
  `GitError` if the branch doesn't exist. No fallback, no suggestion,
  no auto-detection — the run dies with a generic git error.
- **Existing primitives** in [git.ts](../../src/git/git.ts):
  `currentBranch()` (line 224), `branchExists()` (line 260),
  `revParse()` (line 257). **Missing**: a `detectDefaultBranch()` helper
  that walks `git symbolic-ref refs/remotes/origin/HEAD` →
  `git config init.defaultBranch` → `main` fallback.

### Feature-branch flag handling

- **MCP `yaao_convert`** ([tools.ts:162-175](../../src/mcp/tools.ts#L162-L175)):
  takes `featureBranch` arg, writes verbatim to `plan.featureBranch` in
  the generated YAML. **Works.**
- **MCP `yaao_run`** ([tools.ts:273-298](../../src/mcp/tools.ts#L273-L298)):
  takes runtime `featureBranch` override, empty string clears it.
  Precedence is documented: `runtime arg > plan.featureBranch > none`.
  **Works.**
- **CLI `yaao plan`**: no `--feature-branch` flag. The planner can't be
  pointed at a target integration branch from the command line.
- **CLI `yaao convert`**: no `--feature-branch` flag (the MCP tool's
  argument has no CLI exposure).
- **CLI `yaao run`**: has `--base-branch` ([run.ts:48](../../src/cli/commands/run.ts#L48))
  which overrides `plan.config.base-branch`, but no `--feature-branch`
  to override `plan.featureBranch`.

The MCP and CLI surfaces are out of sync; F14.9 closes the CLI side.

## Design

### Part A — Base-branch detection

**A1. New git primitive `detectDefaultBranch(cwd)`** in
[src/git/git.ts](../../src/git/git.ts):

```ts
async detectDefaultBranch(cwd?: string): Promise<string> {
  // 1) Remote's default — most reliable for repos with origin
  const sym = await run(['symbolic-ref', '--short', 'refs/remotes/origin/HEAD'], cwd);
  if (sym.exitCode === 0) {
    const ref = sym.stdout.trim();   // e.g. "origin/main"
    const idx = ref.indexOf('/');
    if (idx > 0) return ref.slice(idx + 1);
  }
  // 2) User's preferred default for new repos
  const cfg = await run(['config', '--get', 'init.defaultBranch'], cwd);
  if (cfg.exitCode === 0 && cfg.stdout.trim()) return cfg.stdout.trim();
  // 3) Final fallback
  return 'main';
}
```

The helper is best-effort and always returns *something*, so callers
don't need to handle missing git or detached HEAD specially.

**A2. Use it at init time** in [src/init/scaffold.ts](../../src/init/scaffold.ts):

- `buildDefaultConfigJson(opts)` takes an optional
  `detectedBaseBranch: string` parameter (default `'main'`). When
  passed, writes it into `defaults.base-branch`.
- [cli/commands/init.ts](../../src/cli/commands/init.ts) calls
  `git.detectDefaultBranch(cwd)` after the existing git-repo check and
  passes the result through.
- Log the detected branch to the user: `detected base-branch: master`.
- A new `--base-branch <name>` flag on `yaao init` lets the user pin
  the value explicitly, skipping detection.

**A3. Validate at run time** in [src/exec/runner.ts](../../src/exec/runner.ts):

After plan resolution but before worktree creation (around the existing
`policy = resolveBranchPolicy(opts.plan)` at line 118):

```ts
const baseExists = await git.branchExists(policy.baseBranch, opts.rootDir);
if (!baseExists) {
  throw new YaaoError({
    code: 'YAAO_BASE_BRANCH_MISSING',
    message: `base-branch '${policy.baseBranch}' not found in this repo`,
    hint: `the repo's default branch may be different. Run \`git branch\` to see available branches, then set defaults.base-branch in yaao.config.json or pass --base-branch <name>.`,
  });
}
```

Same check belongs in `yaao_run`'s MCP handler so the error is
consistent.

The existing typo-warning at [tools.ts:229-243](../../src/mcp/tools.ts#L229-L243)
covers `plan.featureBranch` only; add a parallel one for
`plan.config.base-branch` so the gap surfaces at convert time too.

### Part B — CLI `--feature-branch` plumbing

**B1. `yaao plan --feature-branch <name>`**:

Today's planner skill doesn't know about feature branches at all — it
emits plan markdown/Spec Kit and the converter assigns task structure
later. So `--feature-branch` on `yaao plan` doesn't change the planner's
behaviour; it threads through into the planner skill's `inputs` and the
generated plan body's front-matter / metadata block so the converter
picks it up.

Practically:

- Add `--feature-branch <name>` to [cli/commands/plan.ts](../../src/cli/commands/plan.ts).
- Pass to `runPlanner({ ..., featureBranch })`.
- The planner skill ([prompt.md](../../src/skills/builtin/yaao-planner/prompt.md))
  gains an `feature-branch` input. When set, the planner adds a
  `feature-branch: <name>` line to the plan's metadata block so the
  converter reads it.

**B2. `yaao convert --feature-branch <name>`**:

- Add `--feature-branch <name>` to [cli/commands/convert.ts](../../src/cli/commands/convert.ts).
- Thread through to `convertPlan({ featureBranch })` (the converter
  already takes this option per [convert.ts:23-28](../../src/converter/convert.ts#L23-L28)).
- Precedence: CLI flag > plan-body `feature-branch:` metadata >
  absent.

**B3. `yaao run X --feature-branch <name>`**:

- Add `--feature-branch <name>` to [cli/commands/run.ts](../../src/cli/commands/run.ts)
  alongside the existing `--base-branch`.
- Apply as a runtime override on the resolved plan, same shape as the
  MCP runtime override at [tools.ts:294-298](../../src/mcp/tools.ts#L294-L298):
  empty string clears `plan.featureBranch`; any other value sets it.

**B4. Documented precedence chain**:

For both base-branch and feature-branch:

1. CLI flag (`--base-branch` / `--feature-branch`) — highest
2. Plan-file YAML (`plan.config.base-branch` / `plan.featureBranch`)
3. Workspace config (`defaults.base-branch`) — base only;
   featureBranch has no workspace default by design
4. Detected default (Part A) — base only; final fallback

phase-3 notes.

## Acceptance criteria

### Base-branch detection

- `yaao init` in a master-default repo writes `defaults.base-branch: master`
  to the scaffolded config and logs the detection result.
- `yaao init` in a main-default repo writes `main`.
- `yaao init` in a repo with no remote (fresh `git init`) reads
  `git config init.defaultBranch`; falls back to `main` if neither is
  set.
- `yaao init --base-branch trunk` writes `trunk` regardless of
  detection.
- `yaao run` against a plan whose `base-branch` doesn't exist fails
  pre-flight with `YAAO_BASE_BRANCH_MISSING` and the actionable hint.
  No worktree is created.
- `yaao_run` MCP tool emits the same error.

### `--feature-branch` plumbing

- `yaao plan "x" --feature-branch feat/foo` produces a plan whose
  metadata records the feature branch; `yaao convert` of that plan emits
  YAML with `plan.featureBranch: feat/foo`.
- `yaao convert .yaao/plans/x.md --feature-branch feat/foo` writes
  `plan.featureBranch: feat/foo` to the exec YAML, overriding the
  source plan's metadata if present.
- `yaao run x.yaml --feature-branch feat/foo` overrides whatever
  `plan.featureBranch` is in the YAML; an empty string clears it.
- `yaao run x.yaml --feature-branch ''` runs trunk-based, matching the
  MCP `yaao_run` semantics.
- All three flags are documented in `--help` output.
- The new behaviour matches the MCP equivalents byte-for-byte (same
  validation, same warning shape).

## Out of scope

- **Auto-creating the base-branch if it doesn't exist.** Hard fail
  with a clear error; the user should know which branch their work
  lands on.
- **Auto-rewriting existing plan YAMLs that hard-code `main`.** Plans
  with `base-branch: main` keep working; the validation only fires when
  the branch actually doesn't exist.
- **A `yaao migrate` command for old configs written before A1.**
  Detection runs at *init* time; once written, the config is the
  source of truth. Users can re-run `yaao init` (it's idempotent for
  unrelated fields) or hand-edit.
- **CLI flag for `defaults.base-branch` at runtime separate from
  `--base-branch` on run.** The existing flag already overrides the
  plan's base-branch per invocation; no second flag needed.
- **Workspace-level `defaults.feature-branch` config.** By design —
  feature branches are per-plan or per-run, not a workspace default.
- **Renaming `--base-branch` to `--branch`.** The shipped flag name
  stays. The two concepts (base / feature) are distinct enough that
  collapsing them into one ambiguous `--branch` flag would regress
  clarity.
