# F14.5 Web Plan Editor

**Phase**: 14 — Web Viewer
**Priority**: Medium
**Dependencies**: F14.1, F14.2

## Goal

An in-browser YAML editor for execution plans (`.yaao/exec/<slug>.yaml`) and implementation plans (`.yaao/plans/<slug>.md`) that validates on every keystroke and writes back through `PUT /api/plans/:slug/raw`. Pairs with the DAG view (F14.2) so the user can edit a plan and watch the graph update without leaving the page.

The "edit text in your IDE, refresh the browser" workflow works without this — F14.2's live reload already handles it. F14.5 exists for users who want the whole loop in one window, which is the natural shape once the web viewer is the primary surface for everything else.

## Pages

- `/plans/:slug/edit` — split-pane editor (YAML left, DAG right).

## Layout

- Top bar: slug, save state ("saved" / "unsaved changes" / "validation errors (3)"), save button, "Reset to disk" button.
- Left pane (~50%): Monaco editor with YAML mode and the execution-plan JSON Schema attached (`/api/plans/schema`). This drives autocomplete and inline diagnostics.
- Right pane (~50%): the F14.2 DAG view of the *unsaved* edited plan. Re-renders on debounced input (~250 ms). Tasks added/removed in the YAML appear/disappear in the graph; the user gets immediate visual feedback that they wrote what they meant to.
- Bottom strip: validation issue list. Each row is clickable to jump to the issue's line in the editor.

## Editor stack

- **Monaco** (the VS Code editor): YAML support via `monaco-yaml`, JSON-Schema-aware autocomplete and diagnostics. Bundled in `dist/web/`.
- Save shortcut: ⌘S / Ctrl-S. Same code path as the save button.
- Undo/redo are Monaco's built-in.

## Validation pipeline

Two layers, both must pass before the save button enables:

1. **Schema validation (client-side)**: monaco-yaml runs the JSON Schema in the browser. Surfaces typos, type mismatches, missing required fields as you type. Cheap.
2. **Server validation (on save)**: `PUT /api/plans/:slug/raw` runs the full `validatePlan` pipeline (DAG checks, dep-cycle, ID uniqueness, dep references). Rejects with structured issues; the editor surfaces them on the bottom strip without writing.

The two layers exist because the JSON Schema is necessary-but-not-sufficient — a structurally valid plan can still have a dependency cycle that only the runtime resolver catches.

## Git awareness

The editor surfaces the file's git state, mirroring F14.4's "tracked" column:

- **Untracked**: yellow banner — "this plan isn't committed; runs will refuse to start unless you commit it (or pass `--commit-plan`)."
- **Dirty**: yellow banner — "the saved file has uncommitted changes vs. HEAD."
- **Clean + tracked**: green dot in the bar; no banner.

The banners are advisory. Saving from the editor never refuses based on git state — that's the runner's job. The editor's job is making the state visible.

## Live reload protection

`/api/plans/:slug/watch` (F14.1) fires when the underlying file changes — e.g. the user edits the plan in their IDE while the editor is open, or another tool rewrites it. Behavior:

- If the editor has **no unsaved changes**: reload the file silently; the editor and graph update.
- If the editor has **unsaved changes**: surface a non-modal banner — "the file changed on disk while you were editing. Show diff / Discard my changes / Keep editing." No automatic overwrite, no silent loss.

## Restrictions

- **Create new plan**: a small "New" button in the page header. Posts to `PUT /api/plans/:slug/raw` with a stub template the user fills in. The slug is required upfront.
- **Delete plan**: a "Delete plan" action in an overflow menu — confirms, then `DELETE /api/plans/:slug`. F12.6's watcher equivalent for plans (the F12.6 hot-reload pattern, generalized to `.yaao/plans/` / `.yaao/exec/`) propagates the deletion to the DAG view and the workspace page without a refresh.
- **Plan rename**: not in the editor — rename the file in git directly. Renaming has lineage implications (the worktree cache key includes plan name; rename invalidates existing worktrees) which deserve a tighter flow than a text input.

## Acceptance Criteria

- Editing a task's `prompt` produces no DAG change; editing `depends:` produces an immediate edge update (within ~250 ms debounce).
- Saving with a schema violation (e.g. missing required `agent:`) shows the issue in the editor and does not write the file.
- Saving a plan with a dependency cycle fails server-side; the client surfaces the structured `YAAO_PLAN_INVALID` issue and does not write.
- Editing in the IDE while the editor has unsaved changes shows the "file changed on disk" banner; the user choosing "Show diff" reveals the actual difference; "Discard my changes" reloads from disk; "Keep editing" leaves both states intact (next save resolves).
- The plan's `tracked` / `dirty` state from `git` is rendered correctly and updates after each save.
