# F14.1 `yaao-distiller` Built-in Skill

**Phase**: 15 — Session → Skill Distillation
**Priority**: Critical
**Dependencies**: F8.1 (skill format)

## Goal

A built-in skill that takes a chat-session transcript and produces a **generalized**, reusable yaao skill: a draft `skill.yaml` + `prompt.md` pair ready to be written to `.yaao/skills/<name>/`. The whole product lives in this prompt — the rest of Phase 14 is plumbing around it.

## Location

`src/skills/builtin/yaao-distiller/` — sibling of `yaao-planner` and `yaao-converter`. Mirrors their two-file layout:

```text
src/skills/builtin/yaao-distiller/
├── skill.yaml
└── prompt.md
```

## `skill.yaml`

```yaml
name: yaao-distiller
version: 1
description: Distill a chat-session transcript into a reusable, generalized yaao skill.
appliesTo:
  agents: [claude-code, cursor, copilot, codex, api]
tools:
  - read_file
  - write_file
  - list_files
inputs:
  - name: session
    description: Structured self-summary of the calling agent's conversation (a `SessionRecord` per F14.2). Always supplied inline by the invoking agent — yaao never reads IDE-internal transcript stores.
    required: true
  - name: name
    description: Slug for the new skill (kebab-case). If omitted, the distiller proposes one.
    required: false
  - name: skill-description
    description: One-line description of when this skill should be invoked. If omitted, the distiller drafts one.
    required: false
  - name: existing
    description: Path to an existing skill directory to refine (see F14.5). If set, output evolves the existing skill rather than producing a new one.
    required: false
  - name: out-dir
    description: Where to write the skill. Defaults to .yaao/skills/<name>/.
    default: .yaao/skills/
trigger:
  manual: true
```

## Prompt Design

The prompt drives a three-stage process. Each stage is explicit in the body so the agent doesn't conflate them.

### Stage 1: Identify the pattern

Read the transcript. Identify exactly one *generalizable task type* the user accomplished — e.g. "add a REST endpoint with validation + tests in this repo's conventions." If the session contains multiple unrelated tasks, ask the user which one to distill (do **not** silently pick one or merge them).

### Stage 2: Separate signal from instance

For the chosen task type, produce two lists:

**Keep (signal):**

- Conventions discovered or corrected mid-session (e.g. "endpoints live in `src/api/<resource>/`, not `src/routes/`").
- File-layout decisions (where things go and why).
- Ordered steps that actually worked (the final approach, not the false starts).
- User corrections (`don't do X / always do Y`) — verbatim if short, paraphrased if long.
- Tools / commands that were necessary (validation scripts, lint targets, test runners).
- Gotchas the user pointed out (`this codebase wraps errors with X`, `the test runner needs Y`).

**Drop (instance):**

- Specific entity names (`POST /widgets` → `POST /<resource>`).
- Debugging detours that didn't pan out.
- One-off compromises tagged as temporary in the session.
- Casual chat, meta-discussion about the session itself.

The agent must produce these lists *before* drafting the skill body, and include them as a "## Distillation notes" section appended to the bottom of `prompt.md` (not consumed at runtime; preserved as a paper trail and to make refinement (F14.5) tractable).

### Stage 3: Emit the skill

Produce two artifacts:

**`skill.yaml`** — name (proposed or supplied), `version: 1` on initial creation (refinement does *not* bump this — see F14.5), a tight one-line description, `appliesTo.agents: [claude-code, cursor, copilot, codex, api]` unless the session is clearly agent-specific, declared inputs derived from the variability in the session (the things that *changed* between the user's example and a future re-use).

**`prompt.md`** — the generalized procedure. Structure:

1. *When to use this skill* (one paragraph, mirrors `skill.yaml` description but with concrete trigger conditions).
2. *Conventions in this codebase* (the "Keep" list from Stage 2, as bullets).
3. *Procedure* (numbered steps; uses `{{input}}` placeholders for declared inputs).
4. *Anti-patterns* (the user's corrections from the session).
5. *Distillation notes* (Stage 2 lists, preserved verbatim for future refinement).

## Generalization Rules (in the prompt)

These are written into `prompt.md` as explicit instructions to the agent:

- **Replace, don't redact.** Specifics become placeholders, not gaps. `POST /widgets` → `POST /{{resource}}`, not `POST /...`.
- **Promote inputs from variability.** Anything that varied between what the user *did* and what they'd plausibly do next time becomes a declared input.
- **One skill, one task.** If the session covered two distinct task types, pick one and tell the user the other was dropped.
- **Don't include code blocks from the session verbatim** unless the snippet *is* the deliverable (e.g. a required boilerplate). Code in the session is usually instance, not signal.
- **Cite by path, not by content.** `auth lives in src/auth/middleware.ts` is more durable than pasting the middleware code.
- **Surface the user's "why."** Where the session reveals motivation (`we do it this way because of incident X`), preserve it as a brief rationale line.

## Validation expected from the caller

The skill body itself does not validate its own output — that is F14.3's job. But the prompt explicitly tells the agent: every `{{placeholder}}` in the generated `prompt.md` must correspond to a declared input in the generated `skill.yaml` (matching the rule in [format.ts:135](../../src/skills/format.ts#L135)).

## Why this design (and not "auto-summarize the session")

A literal session summary is the wrong artifact. It would:

- Contain specifics that don't apply to the next task.
- Embed false starts the user already abandoned.
- Read as a story, not a procedure.

The distiller's job is *generalization*, not summarization — the "Keep vs. Drop" stage exists specifically to force that distinction. A summary-style skill is the failure mode this design is built to prevent.

## Acceptance Criteria

The core risk for this feature is *the distiller producing a session summary instead of a generalized procedure*. Generic structural tests (placeholder match, valid YAML) don't catch that failure mode — they pass on a bad summary just as well as on a good distillation. The acceptance criteria below are designed to test for actual generalization, not shape.

- Given a realistic Claude Code session transcript (fixture: adding a single API endpoint), the distiller produces a skill that:
  - Has a kebab-case `name` matching the user's input or a reasonable proposal.
  - Declares inputs for **every entity that varies between the captured session and a plausible re-invocation** — at minimum the resource name and a description of the new endpoint's purpose. The "what varied" set is derived from the fixture and asserted explicitly.
  - Cites the project's directory conventions discovered in-session by **path**, not by code body (e.g. mentions `src/api/<resource>/` as the location, not the contents of `src/api/widgets/route.ts`).
  - Contains no entity-specific names from the original session in the `Procedure` section. Tested via a denylist: every concrete identifier the session used (`widgets`, `widget_id`, `widgets_table`, etc.) is asserted absent from the procedure.
  - Contains the **user corrections** from the fixture in the `Anti-patterns` section, with the same prose meaning (verbatim if ≤ 80 chars; otherwise paraphrased but referencing the same constraint).
  - Stage 2's "Distillation notes" appear verbatim at the bottom of `prompt.md` and contain both a Keep list and a Drop list with non-zero entries each.
- Re-invoking the distiller with `existing: <path>` produces an evolved skill, not a duplicate (handed off to F14.5).
- A session containing two unrelated task types causes the distiller to ask which one to distill, not to silently pick or merge. The clarification request includes both task summaries verbatim so the user can answer in one turn.

### What "ambiguous → clarify" means operationally

A session is multi-task when the agent identifies two or more **non-overlapping file sets** that each have their own corrections and their own ordered approach. A single task with a debugging detour (the agent tried path A, was told to use path B, succeeded) is **not** multi-task — the detour is signal that goes in the Anti-patterns section, not a separate skill. This rule lives in the prompt; a fixture (`single-task-with-detour.jsonl`) asserts the distiller does not split it.

## Tests

- `tests/phase-14/distiller/fixtures/cc-add-endpoint.jsonl` — realistic Claude Code transcript adding a single API endpoint, with at least three user corrections and one false-start detour.
- `tests/phase-14/distiller/fixtures/multi-task.jsonl` — two unrelated tasks in one session (e.g. add endpoint + fix migration).
- `tests/phase-14/distiller/fixtures/single-task-with-detour.jsonl` — one task, one mid-session correction; must NOT split.
- `tests/phase-14/distiller/generalization.test.ts` — the "what varied" set from the fixture appears as declared inputs; the entity denylist is absent from the procedure body. This is the load-bearing test.
- `tests/phase-14/distiller/conventions-by-path.test.ts` — conventions section cites paths, not pasted code blocks > 5 lines.
- `tests/phase-14/distiller/corrections-preserved.test.ts` — every user correction in the fixture has a matching anti-pattern line.
- `tests/phase-14/distiller/distillation-notes-shape.test.ts` — Keep + Drop lists are non-empty.
- `tests/phase-14/distiller/placeholders-match-inputs.test.ts` — every `{{x}}` has a declared input (already enforced by `validateSkill`; this is a defense-in-depth check at the distiller layer).
- `tests/phase-14/distiller/multi-task-session.test.ts` — ambiguous transcript → clarification request, not silent merge.
- `tests/phase-14/distiller/detour-not-split.test.ts` — single-task-with-detour input emits one skill, with the detour as anti-pattern.
- `tests/phase-14/distiller/golden-skill.test.ts` — supplementary structural match against a checked-in golden (allowance for prompt-body wording). Useful as a regression backstop, not a primary acceptance signal.
