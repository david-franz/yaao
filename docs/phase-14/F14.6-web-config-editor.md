# F14.6 Web Config Editor

**Phase**: 14 — Web Viewer
**Priority**: Medium
**Dependencies**: F14.1, F14.5

## Goal

An in-browser editor for `yaao.config.json` — the same file `yaao init` scaffolds and the rest of yaao reads at startup. Schema-validated, secrets-aware, live-reloading. Together with F14.5 (plan editor) and F14.4 (workspace) this closes the "everything I need to operate yaao lives in the web viewer" loop.

## Pages

- `/config` — single-pane Monaco editor + a settings-style summary view.

## Layout

Two views on the same data, toggled by a tab at the top of the page:

### Form view (default)

A structured settings UI rendered from the JSON Schema. Sections:

- **Defaults**: agent, model, max-parallel, base-branch, worktree-root, permissions.
- **Agents**: per-agent enable toggle + bin path + default-model. Disabled agents hide their detail.
- **API providers**: a row per provider with name + `api-key` placeholder (read-only literal masked; placeholders editable as text). A "Test resolution" button calls the F15.1 doctor for that provider and shows the result.
- **Merge**: strategy, on-conflict, history, conflict-resolver.
- **Run gates**: `require-tracked-plan` (the gate from the planCommit work).
- **MCP servers**: per-server command + args + env. Inline help points at `yaao serve --web`.
- **ctx-sys**: enabled, auto-spawn, require-query.
- **Plan defaults**: format, speckit, out-dir, exec-dir.

This is the surface most users will live in. Schema-driven so it stays in sync with `ConfigSchema` automatically; new fields appear when the schema updates without per-field UI work.

### Raw view

Monaco editor with the JSON-Schema-aware setup. Same as F14.5's plan editor stack but pointed at `yaao.config.json` and `/api/config/schema`. Available for users who want to copy/paste blocks or write configs that don't yet have a form representation.

## Validation pipeline

Both views feed the same pipeline:

1. **Schema validation** in-browser via the JSON Schema.
2. **Server validation** on save (`PUT /api/config/raw`): full Zod parse via `ConfigSchema.safeParse`, plus a secrets-leakage scan. Rejects with structured issues.

The secrets scan deserves its own callout — see below.

## Secrets handling (the load-bearing rule)

The config file allows API keys as either:

- **Placeholder**: `"${OPENAI_API_KEY}"` — the actual value lives in the env (or `.yaao/secrets.local.json`).
- **Literal**: `"sk-..."` — strongly discouraged; yaao already throws `YAAO_LITERAL_SECRET` from `loadConfig` when it sees one.

The editor mirrors that contract:

- The form view's API-key field renders the **placeholder syntax** (`${...}`), not the resolved value. Even if the resolved value is in memory at server-side, the editor never receives it. The "Test resolution" button calls the doctor and reports success/fail without revealing the value.
- `PUT /api/config/raw` runs the same literal-secret detector `loadConfig` uses ([src/config/loader.ts](../../src/config/loader.ts)). A POST containing a literal API key fails with `YAAO_LITERAL_SECRET` + a hint pointing at the placeholder form. The editor surfaces the field name explicitly.
- The "view raw config" path (`GET /api/config/raw`) returns placeholders, never resolved values. The `GET /api/config` (resolved) path is only used by tooling that needs the live values; the editor never calls it.

This means a user can never accidentally commit a literal key via the editor: it'd be rejected server-side before reaching the file.

## Live reload

`/api/config/watch` (F14.1) fires on disk writes. Same flow as F14.5:

- No unsaved changes → silent reload.
- Unsaved changes → non-modal banner with Show diff / Discard / Keep editing.

This also means the editor cooperates with `yaao init` and `yaao doctor --fix` — if either rewrites the config from the CLI, the open editor surfaces the change instead of overwriting it.

## Restart awareness

Some config changes only take effect on restart:

- `mcp-servers.<name>` changes — the MCP server spawn happens at `yaao serve` startup.
- `defaults.worktree-root` — affects where new worktrees land; existing ones stay put.

When the user saves a change of this shape, the editor shows a yellow toast: "This change affects new runs only — in-flight runs and the running yaao serve still use the previous config." For MCP-server changes specifically, a "Reload MCP servers" button appears — when clicked, the server reloads just the `mcp-servers` map and re-spawns affected backends without restarting the whole process.

## Restrictions

- **No secret-write affordance.** The editor never accepts a literal secret; placeholders only. Users wanting to set actual secret values use their shell (`export OPENAI_API_KEY=…`) or `.yaao/secrets.local.json` (not committed; not editable here either — too easy to leak).
- **No config rename / multiple configs.** yaao reads exactly one project config; multiple configs is out of scope for v1.
- **No global config editor** (`~/.yaao/config.json`). The web editor edits the project config only. Global config is rarely touched and editing it in the user's shell is fine.

## Acceptance Criteria

- Form view renders every field from the JSON Schema; new schema fields appear automatically.
- Saving with a literal API key in any provider field is rejected with `YAAO_LITERAL_SECRET` and the field-path; the file is not overwritten.
- Saving via the raw view goes through the same Zod parse as `loadConfig`; structurally invalid JSON is rejected client-side, semantically invalid config server-side.
- `mcp-servers.*` changes surface the "reload MCP servers" affordance; clicking it restarts only the affected backends and the existing `tools/list_changed` notifications fire.
- `/api/config/raw` never includes a resolved secret value; only the `${VAR}` form.
- Editing the file in the user's IDE while the editor has unsaved changes shows the conflict banner.
