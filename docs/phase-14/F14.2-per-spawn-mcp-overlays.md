# F14.2 Per-Spawn MCP Overlays for Cursor / Codex / Copilot

**Phase**: 14 — Integration Correctness
**Priority**: High
**Dependencies**: F4.1 (backend interface), F7.2 (MCP server registration), F8.x (skill emitters)

## Goal

Cursor, Codex, and Copilot agents should reach the **per-run** MCP servers
(yaao's own server, ctx-sys when enabled, `context.mcp-servers:` declared
in the plan) the same way Claude Code already does — through a transient
config file written at spawn time and removed when the agent exits.

Today this works only for Claude Code. Three of four CLI backends silently
drop the `mcpServers` argument they receive at
[lifecycle.ts:249](../../src/exec/lifecycle.ts#L249).

## The gap

[lifecycle.ts:240-261](../../src/exec/lifecycle.ts#L240-L261) passes
`mcpServers` to every backend's `spawn()`. Only
[ClaudeCodeBackend.spawn](../../src/agents/claude-code.ts#L131) reads it:
it writes a temp `mcp.json` via [writeMcpConfig](../../src/agents/claude-code.ts#L154)
and passes the path with `--mcp-config`. Cursor/Codex/Copilot inherit
from [SubprocessBackend.spawn](../../src/agents/subprocess.ts#L68-L95)
which never references the field.

The static `yaao skills install` emitters DO write each agent's MCP
config (`.cursor/mcp.json`, codex TOML overlay, `.vscode/mcp.json`) —
but that path can't carry **per-run** state. ctx-sys's socket path
changes per run; `context.mcp-servers:` is per-plan; you can't write
those into a checked-in config file the user owns.

So today on Cursor/Codex/Copilot:

- `context.ctx-sys.enabled: true` produces a ctx-sys server the agent
  never sees.
- `context.mcp-servers: { ... }` in a plan is silently ignored.
- Even yaao's own MCP server (declared via the static emitters) works
  only because it's the same `yaao serve` command in every run; if a
  user ever needed per-run yaao state, it wouldn't reach the agent.

## Design

Each backend's `spawn()` overrides write a per-spawn MCP overlay in
the format the underlying CLI accepts, point the CLI at it, and clean
up on completion. Pattern matches
[ClaudeCodeBackend.spawn](../../src/agents/claude-code.ts#L131-L151).

### Cursor

Cursor reads `.cursor/mcp.json` from the workspace root. Backend writes
a temp file with the merged set (per-spawn servers + whatever
`yaao skills install` would write) and points Cursor at it via an
environment variable or an `--mcp-config` flag if `cursor-agent` adds
one in its current version. Until Cursor exposes a flag, the practical
mechanism is the **overlay swap** pattern documented in
[docs/phase-4/F4.3-cursor-backend.md](../phase-4/F4.3-cursor-backend.md):
back up any existing `.cursor/mcp.json`, write the per-spawn merged
file, restore on completion. The backup/restore is keyed on
`(runId, taskId)` so concurrent spawns within a run don't fight (and,
post Phase 16 F16.1, the runId entropy makes cross-run concurrent
overlays safe too).

If the user's existing `.cursor/mcp.json` already contains the static
`yaao` entry from `yaao skills install`, the overlay merges per-run
servers on top, preserving the user's entries.

### Codex

Codex reads `~/.codex/config.toml`. The shipped emitter
([src/skills/emitters/codex.ts](../../src/skills/emitters/codex.ts))
already writes `.yaao/codex-mcp-overlay.toml` as a yaao-owned file
listing the MCP servers — but Codex doesn't load that file directly.
The current contract is that the user references it from their
`~/.codex/config.toml` manually (documented in
[F8.5](../phase-8/F8.5-codex-emitter.md)).

For F14.2: write a per-spawn TOML at
`.yaao/runs/<runId>/<taskId>/codex-config.toml` containing the merged
MCP server set and pass it to Codex via
`--config-overlay <path>` (or whatever flag the shipped Codex version
exposes — if none exists, fall back to writing into
`~/.codex/config.toml` with explicit backup/restore, same shape as
Cursor).

### Copilot

`gh copilot agent run` reads its MCP servers from `.vscode/mcp.json`.
Same overlay-swap pattern: write a per-spawn `.vscode/mcp.json` with
the merged set, run the spawn, restore the user's original on
completion. The backup is keyed on `(runId, taskId)`.

### Shared primitive

Factor the overlay-swap pattern into a helper —
`src/agents/mcp-overlay.ts` exporting:

```ts
export interface OverlayHandle {
  /** Path of the per-spawn file the backend should point its CLI at. */
  path: string;
  /** Restore the user's original file (idempotent). */
  restore(): Promise<void>;
}

export function writeOverlay(opts: {
  agent: AgentName;
  cwd: string;
  servers: McpServerConfig[];
  runId: string;
  taskId: string;
}): OverlayHandle;
```

The helper handles back up + write atomically; backends just call it.
This keeps Cursor/Codex/Copilot backends < 20 LOC of net new code each.

### Concurrency

Two task spawns within one run for the same agent (e.g. two cursor
tasks running in parallel) share `cwd` and would race on
`.cursor/mcp.json`. Mitigations:

- Per-spawn overlay file lives under
  `.yaao/runs/<runId>/<taskId>/overlay-<agent>.<ext>` and the backend
  uses a CLI flag where possible (avoiding the cwd file altogether).
- Where the backup-restore-cwd-file pattern is the only option (Cursor
  pre-flag), `mcpOverlay.writeOverlay` serializes writes via a
  per-cwd `Mutex` and the restore on completion happens before the
  next sibling spawn picks up its overlay. Phase 16 F16.1's worktree
  isolation means each task already runs in its own worktree directory,
  so the shared-`cwd` race only applies for cursor/copilot tasks whose
  CLIs read from the project root rather than the worktree.

## Acceptance criteria

- For each of {cursor, codex, copilot}: a unit test spawns the backend
  with a synthetic `mcpServers: [{ name: 'fake', command: 'echo', args: ['hi'] }]`
  and asserts the CLI receives the server entry (via a recorded-call
  fake of the underlying CLI binary).
- An integration test for ctx-sys + cursor: with `context.ctx-sys.enabled: true`,
  spawn a cursor task; assert the per-spawn overlay file contains a
  `ctx-sys` entry pointing at the run's socket path.
- An integration test for `context.mcp-servers:`: a plan declaring
  a custom MCP server passes it through to Codex's spawn config.
- The user's pre-existing `.cursor/mcp.json` (or `.vscode/mcp.json`) is
  byte-identical after the spawn completes, both on success and on
  failure paths.
- Two concurrent cursor spawns (post-Phase 16 F16.1) don't trample each
  other's overlay; each task sees only the servers it was given.

## Out of scope

- **Replacing the static `yaao skills install` emitters.** Those still
  write the user-visible config files (and the user's editor reads them
  outside of a yaao run). F14.2's overlays are *additive* per-spawn
  state, not a replacement for the static path.
- **Auto-detecting the right Cursor/Codex/Copilot version's MCP flag.**
  Pin to the modern shape; document the minimum supported version in
  each backend doc.
- **A unified MCP-config primitive across all four backends.** The
  shared helper in `src/agents/mcp-overlay.ts` is the right unit of
  reuse; a full common backend abstraction (single MCP-config writer
  used by all four) is a v2 cleanup.
