# F14.8 Config UX & Model Discovery

**Phase**: 14 — Integration Correctness
**Priority**: Medium (substantial user-facing improvements; nothing in here is "broken behaviour" the way F14.1 was, but together they fix the config block's discoverability)
**Dependencies**: F14.1 (enable-disable plumbing + planner config-awareness), F14.6 (working OpenAI/OpenRouter providers — needed for the api backend to be a sensible `plan.agent` choice)

## Goal

Big sweep of config + UX cleanup surfaced by the v1 pre-flight. Each
piece is small but together they make the config block and the
`yaao agents` command actually usable for someone who isn't reading
source. Three thematic groups:

- **Group A — Config shape cleanup**: dead/misleading fields removed,
  defaults aligned with intent, undocumented fields documented.
- **Group B — Model discovery**: `yaao agents --models` + per-backend
  static catalog so users can answer "what models can I use here?"
  without grep-ing vendor docs.
- **Group C — Schema reachability**: fix the broken `$schema` URL so
  editor autocomplete actually works.

## Group A — Config cleanup

### A1. `plan.agent` / `plan.model` / `plan.api` config block

Today [`yaao plan`](../../src/cli/commands/plan.ts#L42) uses
`defaults.agent` (with `--agent` override). The user can't say "for
planning, use api/anthropic with claude-opus-4-7; for task execution,
use cursor" without overriding the top-level default — which then
affects every other command.

Add a `plan` config block parallel to the existing `plan` block (which
holds `format`, `out-dir`, etc.):

```jsonc
{
  "defaults": { "agent": "cursor" },
  "plan": {
    "agent": "api",
    "model": "claude-opus-4-7",
    "api": { "provider": "anthropic" },
    "format": "markdown",
    "out-dir": ".yaao/plans"
  }
}
```

**Precedence** (composes with F14.1's enabled-walk):

1. `--agent` / `--model` flag passed to `yaao plan`
2. `plan.agent` / `plan.model` in workspace config
3. `defaults.agent` / agents.X.default-model / `defaults.model`
   (the chain F14.1's fallback walks)

`plan.api.provider` only matters when the resolved agent is `api`;
otherwise ignored.

**Lift the "api backend not supported by yaao plan" restriction.**
[plan.ts:101](../../src/cli/commands/plan.ts#L101):

```ts
case 'api':
  throw new Error('the `api` backend is not supported by yaao plan in MVP; use a CLI agent');
```

Was correct when the API path was Anthropic-only and the planner was
already sweating. With F14.6 shipping working OpenAI + OpenRouter
providers and the planner becoming a real first-class agent invocation,
this throw stops making sense. Remove it; route the api backend through
the same `runPlanner` path the CLI backends use.

### A2. Remove dead `plan.speckit`

[schema.ts:97](../../src/config/schema.ts#L97) declares `plan.speckit:
boolean = false` and [scaffold.ts:34](../../src/init/scaffold.ts#L34)
writes it. **Nothing reads it.** `plan.format: 'markdown' | 'speckit'
| 'both'` is the actual control. Delete the field from the schema and
the scaffold output. Existing configs with the field are silently
accepted (the schema's `.strict()` mode currently rejects unknown
fields, so the migration is: relax `.strict()` for the `plan` object
specifically OR add an explicit handler that strips the legacy field
during load). Recommend the strip-on-load path — keeps `.strict()`
elsewhere.

### A3. Flip `merge.history` default from `merge` to `rebase`

[schema.ts:39](../../src/config/schema.ts#L39):

```ts
history: z.enum(['merge', 'rebase']).default('merge'),
```

User intent for the default trio is `strategy: 'auto'`,
`on-conflict: 'agent'`, `history: 'rebase'`. The first two already
match; flip the third. Behaviour change: completed task branches land
as replayed commits on the target (linear history) instead of merge
commits per task.

**Forward-only.** Existing in-flight runs are unaffected; resumed runs
read the plan's history setting (which defaults to workspace config at
load time, so a resumed run after this change picks up `rebase` unless
the plan pinned `history: 'merge'` explicitly).

### A4. Document `ctx-sys.auto-spawn`

[schema.ts:90](../../src/config/schema.ts#L90) declares
`'auto-spawn': z.boolean().default(true)` with no inline comment. The
flag is meaningful but only when `ctx-sys.enabled: true` (default
false — most users never see it):

- `auto-spawn: true` (default): yaao calls `ctx-sys serve --socket
  <path>` itself when a run starts.
- `auto-spawn: false`: yaao assumes the user already has
  `ctx-sys serve` running and connects to the project socket.

Add an inline comment to the schema matching the existing comment
style on `merge.on-conflict` and `run.require-tracked-plan`.

### A5. Document model resolution chain

The chain `task.model → agents.<agent>.default-model → defaults.model`
(per [assign-agent.ts:withResolvedModel](../../src/converter/assign-agent.ts#L105-L113))
is undocumented anywhere user-visible. Add:

- A top-level comment in [schema.ts](../../src/config/schema.ts) above
  the `defaults` block explaining the resolution order.
- A subsection in the README's config reference (around line 192) with
  the same chain explicitly written out.

### A6. Document `defaults.permissions: 'allow-all'`

[schema.ts:25](../../src/config/schema.ts#L25). This is the
`bypassPermissions` mode for Claude (and the analogous bypass for the
other agents) — agents run shell commands without prompting. Defensible
because worktrees are isolated, but it's the most security-sensitive
default in the config and isn't called out anywhere. Add:

- Inline comment expanded to: "Default is `allow-all` because tasks run
  in isolated worktrees and the user has already opted in by launching
  the run. Set to `ask` for interactive confirmation or `allow-edits`
  for file-writes-only (bash still prompts). Per-task `permissions:`
  overrides this."
- README config reference: add a paragraph about the security model.

### A7. `defaults.model: 'opus'` cross-agent warning

[schema.ts:18](../../src/config/schema.ts#L18). `opus` is a
Claude-specific shorthand (resolved via
[MODEL_ALIASES](../../src/agents/claude-code.ts#L12)). When
`defaults.agent: 'cursor'` and `defaults.model: 'opus'`, cursor
receives `--model opus` verbatim and probably errors.

Two options:

- **(a) Make `defaults.model` undefined by default** — each agent picks
  its own. Cleanest but changes default behaviour for existing configs.
- **(b) Keep the default but add a validation warning** — at
  `yaao validate` (and the F14.1 run-time validation gate),
  raise `YAAO_PLAN_CLAUDE_ALIAS_ON_WRONG_AGENT` (severity warning) when
  the resolved model is a Claude alias AND the resolved agent isn't
  `claude-code` or `api` with `anthropic` provider.

Recommend **(b)** — fewer breaking changes, clearer signal at the
point of failure.

### A8. Document `mcp-servers` vs `context.mcp-servers` precedence

Workspace config has `mcp-servers` (global); plans have
`context.mcp-servers` (per-plan). The merge order isn't stated
anywhere. Pick: **per-plan `context.mcp-servers` is layered on top of
workspace `mcp-servers`; name-collisions favor the plan's entry.** Doc
this in the schema comment + the README config reference.

Also add a `YAAO_PLAN_MCP_SERVER_OVERRIDE` validation warning when a
plan's `context.mcp-servers` redefines a workspace entry, so users see
the override happening.

## Group B — Model discovery

### B1. Static model catalog per backend

Each backend module exports a `KNOWN_MODELS` array + `KNOWN_MODELS_ASOF`
date:

```ts
// src/agents/claude-code.ts
export const KNOWN_MODELS = [
  { name: 'opus',   canonicalId: 'claude-opus-4-7',          notes: 'alias for the canonical id' },
  { name: 'sonnet', canonicalId: 'claude-sonnet-4-6',        notes: 'alias' },
  { name: 'haiku',  canonicalId: 'claude-haiku-4-5-20251001', notes: 'alias' },
  // ... plus full canonical ids
] as const;
export const KNOWN_MODELS_ASOF = '2026-05-29';
```

Live across all four CLI backends + the three API providers
(`AnthropicProvider`, `OpenAIProvider`, `OpenRouterProvider`). The
`asOf` lets users see how stale the catalog is at a glance.

The catalog is **advisory, not authoritative**: passing a model not
in the catalog is allowed (the backend will surface the vendor's error
if the model is genuinely unsupported). The catalog exists to answer
"what *can* I use?" without grep-ing vendor docs.

### B4. Fix `yaao agents` "exited -1" rendering

[src/agents/subprocess.ts:51-66](../../src/agents/subprocess.ts#L51-L66):

```ts
async isAvailable(): Promise<AvailabilityReport> {
  try {
    const r = await execa(this.opts.bin, ['--version'], { reject: false });
    const code = typeof r.exitCode === 'number' ? r.exitCode : -1;
    if (code !== 0) {
      return { available: false, reason: `${this.opts.bin} --version exited ${code}` };
    }
    // ...
  } catch (err) {
    return { available: false, reason: (err as Error).message };
  }
}
```

When the binary isn't on PATH, execa with `reject: false` doesn't
throw — it returns an object with `r.failed: true` and `r.exitCode:
undefined`. The fallback to `-1` produces user-visible nonsense:
`codex --version exited -1`.

Fix: detect the spawn-failure shape explicitly.

```ts
const r = await execa(this.opts.bin, ['--version'], { reject: false });
if (r.failed && typeof r.exitCode !== 'number') {
  return {
    available: false,
    reason: `binary '${this.opts.bin}' not found on PATH (install it or set agents.<name>.bin in yaao.config.json)`,
  };
}
const code = typeof r.exitCode === 'number' ? r.exitCode : -1;
if (code !== 0) {
  return { available: false, reason: `${this.opts.bin} --version exited ${code}: ${(r.stderr ?? '').toString().trim() || '(no stderr)'}` };
}
```

The Copilot backend's [override at copilot.ts:32](../../src/agents/copilot.ts#L32)
follows the same shape — same fix.

## Group C — Schema reachability

### C1. Fix the `$schema` URL

[init/scaffold.ts:16](../../src/init/scaffold.ts#L16) writes
`$schema: 'https://yaao.dev/schema/config.json'` into every fresh
config. **yaao.dev is not registered.** Editors (VS Code, Cursor)
that try to fetch the schema for autocomplete get nothing.

Phase 14 ship: replace with a working URL until npm publish (Phase 18)
lands.

- **Until Phase 18 ships**: point at a GitHub raw URL targeting the
  in-repo [schema/config.schema.json](../../schema/config.schema.json).
  Format: `https://raw.githubusercontent.com/<owner>/<repo>/main/schema/config.schema.json`.
- **After Phase 18 ships**: point at the published file inside the
  package — `./node_modules/yaao/schema/config.schema.json` (relative
  paths work in most editors) or a `https://yaao.dev/...` URL if the
  domain is stood up.

Pick one for Phase 14; document the migration path in a comment near
the scaffold. Update the README's example config to match.

Tests should HEAD-request the URL to confirm it resolves; skip in
offline CI.

## Acceptance criteria

### Group A

- `plan.agent`, `plan.model`, `plan.api` parse correctly and
  `yaao plan` respects them in the documented precedence order.
- `yaao plan` with `plan.agent: 'api'` runs the planner via the api
  backend without throwing.
- `plan.speckit` is absent from the scaffold output; configs that
  still contain it parse cleanly with the field ignored.
- `merge.history` default at parse time is `rebase`; a config with no
  merge block uses rebase.
- Each documented config field has an inline comment matching the
  existing comment style.
- A plan with `defaults.model: 'opus'` and `defaults.agent: 'cursor'`
  produces `YAAO_PLAN_CLAUDE_ALIAS_ON_WRONG_AGENT` (warning) at
  validate.
- A plan whose `context.mcp-servers` redefines a workspace
  `mcp-servers` entry produces `YAAO_PLAN_MCP_SERVER_OVERRIDE` at
  validate.

### Group B

- Each backend module exports `KNOWN_MODELS` (non-empty) and
  `KNOWN_MODELS_ASOF` (ISO date).
- `yaao agents --models` prints the catalog grouped by agent, with
  aliases marked and `asOf` dates surfaced.
- `yaao agents --models --json` produces structured output.
- `yaao agents --models --agent claude-code` filters to one backend.
- `yaao_models` MCP tool returns the same data as the JSON output.
- `yaao agents` no longer prints `--version exited -1` for missing
  binaries; instead prints `binary '<bin>' not found on PATH`.

### Group C

- A freshly-init'd `yaao.config.json` has a `$schema` field whose URL
  resolves (HEAD request returns 200).
- The README's example config matches.

## Out of scope

- **Dynamic model probing** (calling each CLI's `--list-models` at
  runtime, or each provider's `/v1/models` endpoint). Static catalog is
  right for v1; live probing is a v2 candidate once real users hit
  stale-catalog pain.
- **A web UI model picker** in the Phase 13 viewer. The catalog data
  structure F14.8 ships is consumable; building the picker UI isn't.
- **Versioned schema migration** for the dropped `plan.speckit` field.
  Existing configs with the field are silently accepted (field
  stripped on load).
- **Standing up yaao.dev**. Phase 18 territory; F14.8 ships the interim
  GitHub raw URL.
- **A general-purpose config-migration tool** for any future schema
  changes. Each removed/renamed field is handled inline; a migration
  framework isn't justified by the current churn.
- **Model alias maps for non-Claude backends** (like
  `gpt-fast → gpt-4o-mini` shorthand for OpenAI). v2 if real users
  request it; for now the canonical id is the only accepted shape on
  every backend except claude-code.
