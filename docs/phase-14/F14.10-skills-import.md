# F14.10 `yaao skills import` — Cross-Provider Skill Portability

**Phase**: 14 — Integration Correctness
**Priority**: Medium-High (high leverage for users with existing skill
libraries; not strictly a defect like F14.1/F14.9)
**Dependencies**: F8.1 (skill format), F8.6 (`skills install`),
[F12.6](../phase-12/F12.6-skill-hot-reload.md) (hot reload — so an
imported skill is callable in the same session)

## Goal

A `yaao skills import` command that converts an agent-native skill
format into yaao's portable skill format (`skill.yaml` + `prompt.md`),
making any single-provider skill library available across **all** yaao
agents via the MCP boundary.

A user with a 30-skill Claude library invokes the command once and gets
those skills as `yaao_skill_<name>` MCP tools callable from Claude
Code, Cursor, Copilot, Codex, and the API backend. Same for Cursor
rules, Copilot instructions, Codex `AGENTS.md`, and any markdown file
with a sensible frontmatter shape.

## Why Phase 14

Phase 14's commitment is "any of the five integrations works
confidently." Today, that's only true at the *agent* layer — F14.1
makes enable/disable honest, F14.6 ships the api providers, F14.7
fixes Copilot. But the *skill* layer is still single-provider: a
Claude skill works only on Claude, a Cursor rule only in Cursor. The
user's existing skill investment doesn't carry across the matrix.

F14.10 extends the integration promise from "the agent runs" to "the
user's skills move with them." That's the same shape of fix as F14.1
and F14.9 — close a gap that makes the cross-provider story partial —
not new product surface.

This is distinct from [Phase 17 distillation](../phase-17/PHASE-17.md):
distillation captures *new* skills from finished sessions; F14.10
*imports* skills the user has already written. The two paths
complement each other; both produce valid yaao skills.

## Supported source formats

### Format 1 — Claude Code skills

**Layout**: `.claude/skills/<name>/SKILL.md` (project) or
`~/.claude/skills/<name>/SKILL.md` (user). May include sibling files
under `tools/`, `references/`, or other directories the skill body
refers to.

**Frontmatter shape** (YAML):

```yaml
---
name: refactor-react-hooks
description: Refactor a React component to use hooks
allowed-tools: [Read, Edit, Glob, Grep]
---
```

**Mapping**:

- `name` → `skill.yaml: name`
- `description` → `skill.yaml: description`
- `allowed-tools` → `skill.yaml: tools` (translated to yaao's tool
  identifiers where they overlap; otherwise preserved verbatim and the
  importer logs a "unknown tool name; preserving as-is" note)
- Body of `SKILL.md` → `prompt.md`
- Sibling files (`tools/`, `references/`, etc.) → copied verbatim to
  `.yaao/skills/<name>/<subdir>/`. A footnote in the imported
  `prompt.md` notes their location.

### Format 2 — Cursor rules

**Layout**: `.cursor/rules/<name>.mdc` (single file).

**Frontmatter shape** (YAML in MDC):

```yaml
---
description: Use Tailwind utility-first patterns
globs: ["**/*.tsx", "**/*.jsx"]
alwaysApply: false
---
```

**Mapping**:

- Filename without `.mdc` → `skill.yaml: name`
- `description` → `skill.yaml: description`
- `globs` → `skill.yaml: applies-to-files` (new optional field; see
  F14.10 Schema additions below)
- Body → `prompt.md`
- `alwaysApply: true` → adds a note "this rule was always-applied in
  Cursor" in the prompt's frontmatter so the agent reading the skill
  knows the original intent.

### Format 3 — GitHub Copilot custom instructions

**Layout**: `.github/copilot-instructions.md` (single file, no
frontmatter by convention).

**Mapping**:

- Filename → `skill.yaml: name: github-copilot-instructions` (configurable
  via `--name`).
- First H1 heading or first sentence → `skill.yaml: description`.
- Body → `prompt.md`.
- `skill.yaml: appliesTo.agents` defaults to **all five** since
  Copilot-style "general guidance" usually applies universally.

### Format 4 — Codex `AGENTS.md`

**Layout**: `AGENTS.md` at the project root (single file).

**Mapping**: same as Format 3 — heuristic name + description, full body
to `prompt.md`, broad `appliesTo`.

### Format 5 — Generic markdown frontmatter

**Layout**: any `.md` file with a YAML frontmatter block.

**Mapping**:

- `name` (or filename) → `skill.yaml: name`
- `description` → `skill.yaml: description`
- `tools` (if present) → `skill.yaml: tools`
- `applies-to` or `agents` (if present) → `skill.yaml: appliesTo.agents`
- Body → `prompt.md`

This is the catch-all for users who write skills in a custom format
that resembles claude/cursor but doesn't match exactly.

## CLI surface

```bash
# 1. Scan known sources, report what's importable, prompt for bulk import
yaao skills import

# 2. Auto-detect source format from path
yaao skills import .claude/skills/refactor-react-hooks
yaao skills import .cursor/rules/tailwind-patterns.mdc

# 3. Explicit source format
yaao skills import --from claude .claude/skills/refactor-react-hooks
yaao skills import --from cursor .cursor/rules/tailwind-patterns.mdc
yaao skills import --from copilot .github/copilot-instructions.md
yaao skills import --from codex AGENTS.md
yaao skills import --from generic ./my-skill.md

# 4. Bulk: import every skill matching a glob
yaao skills import --from claude '.claude/skills/*'
yaao skills import --from cursor '.cursor/rules/*.mdc'

# 5. Common flags
#   --scope project|user   target directory (default project)
#   --name <name>          override the derived skill name
#   --dry-run              print what would be written
#   --force                overwrite existing yaao skill
#   --no-install           skip the post-import `yaao skills install`
#   --json                 machine-readable output
```

After write, the importer automatically runs `yaao skills install`
(emit per-agent stubs) unless `--no-install` is set. F12.6's watcher
picks up the new directory and fires `tools/list_changed`, so the
imported skill is callable as `yaao_skill_<name>` in the same MCP
session — no reconnect needed.

## Schema additions (`skill.yaml`)

The import path needs one new optional field:

```yaml
applies-to-files:
  - "**/*.tsx"
  - "**/*.jsx"
```

This preserves Cursor's `globs` semantics so the imported skill carries
the original "use this skill when the agent is working on files
matching X" intent. yaao itself doesn't enforce the field (no
automatic skill selection by file pattern in v1); it's advisory
metadata an MCP-aware agent can read and apply. The field is also
useful for the per-agent emitters: Cursor's `yaao.mdc` can re-emit
the `globs` so a Cursor session sees them natively.

Backward-compatible (new optional field).

## Behaviour details

### Name derivation

- Claude / generic: prefer frontmatter `name`; fall back to directory
  or filename.
- Cursor: filename without `.mdc`.
- Copilot / Codex: hard-coded sensible defaults
  (`github-copilot-instructions`, `codex-agents-md`) overridable via
  `--name`.
- All sources normalized to the F8.1 name shape (lowercase
  kebab-case, leading letter); names that fail normalization produce a
  `YAAO_SKILL_IMPORT_INVALID_NAME` error with a hint to use `--name`.

### Conflict handling

- Existing `.yaao/skills/<name>/` directory: refuse with
  `YAAO_SKILL_IMPORT_EXISTS` unless `--force` is set.
- `--force` overwrites the entire directory (including any sibling
  files copied from Claude `tools/` subdirs).
- The conflict shape mirrors F17.3's emission contract so users see
  consistent semantics between import and distillation.

### Validation

Every imported skill runs through `validateSkill` ([F8.1](../phase-8/F8.1-skill-format.md))
before being written. Failures surface with the source path so the
user can fix the source or hand-edit the imported skill:

```
yaao skills import .claude/skills/refactor-react-hooks
✗ refactor-react-hooks — declared input 'componentPath' not referenced in prompt.md
  source: .claude/skills/refactor-react-hooks/SKILL.md
  hint: remove the unused input from the imported skill.yaml, or add {{componentPath}} to the prompt
```

`--dry-run` reports validation results without writing anything,
useful for a first pass on a large library.

### Atomic writes

Each skill is written via the same atomic-rename pattern F17.3 uses,
so a kill mid-import doesn't leave a half-written directory.

### Audit trail

Every imported skill's `prompt.md` ends with an "Imported from" footer:

```markdown
## Imported from .claude/skills/refactor-react-hooks/SKILL.md (claude) on 2026-05-29
```

The footer is part of the skill body but conventionally trimmed from
agent-facing prompts; it survives in git so users can trace any imported
skill back to its origin.

## MCP tool — `yaao_skills_import`

Mirror surface for MCP clients. Same input shape as the CLI flags
(`source` path, optional `from`, optional `name`, `scope`, `force`,
`dryRun`). Returns the list of written paths + validation outcomes.

Useful for an agent that wants to ask the user "do you have any
existing Claude skills I should import?" and then call the tool
programmatically.

## Acceptance criteria

- `yaao skills import .claude/skills/<name>` produces a valid
  `.yaao/skills/<name>/` that passes `validateSkill`.
- The imported skill registers as `yaao_skill_<name>` via F12.6 hot
  reload within ~250ms; callable from all four CLI agents + the API
  backend in the next turn.
- `yaao skills import .cursor/rules/<name>.mdc` works in one step,
  preserving the `globs` field as `applies-to-files`.
- `yaao skills import .github/copilot-instructions.md` produces a
  skill with the broad `appliesTo` (all five agents).
- `yaao skills import` with no args scans known locations
  (`.claude/skills/`, `~/.claude/skills/`, `.cursor/rules/`,
  `.github/copilot-instructions.md`, `AGENTS.md`) and reports a
  summary.
- `yaao skills import --from claude '.claude/skills/*'` bulk-imports
  every skill matching the glob.
- A Claude skill with `tools/` sibling files: the entire
  `tools/` directory is copied to the imported location.
- Importing a skill whose target already exists fails with
  `YAAO_SKILL_IMPORT_EXISTS`; `--force` overwrites.
- Validation failures during import name the source file path in the
  error, not just the destination.
- `--dry-run` writes nothing; reports what would happen.
- The `yaao_skills_import` MCP tool returns the same outputs as the
  CLI with `--json`.

## Out of scope

- **Two-way sync** (export a yaao skill back to Claude/Cursor format).
  v2 candidate if users want it. The MCP-tool surface is the
  cross-provider story; round-tripping isn't necessary for that.
- **Live shadowing** of native skills as yaao skills without explicit
  import. Explicit beats implicit; users should know which skills
  yaao manages.
- **Semantic tool translation.** If a Claude skill says "use the Read
  tool" and a non-Claude agent's read tool is named differently, the
  importer doesn't rewrite the prompt — the LLM is trusted to interpret
  "Read" as the equivalent operation. Hard semantic translation is a
  v2 candidate.
- **Conflict resolution for skills with the same name as an existing
  yaao skill.** Refuse without `--force`; require explicit override.
  Merge semantics (combining the imported and existing bodies) is a
  Phase 17 refinement concern, not import.
- **URL import** (`yaao skills import https://github.com/x/skill-pack`).
  Separate feature; involves auth, version pinning, trust questions.
  Probably a Phase 18 / post-v1 idea.
- **A skill marketplace.** Same — beyond v1.
- **`yaao skills new <name>` scaffolder.** Adjacent feature, not part
  of F14.10. Could fold into F14.10 if scope feels right; recommend
  separate small feature in a future phase since the use case is
  different (authoring from scratch vs converting existing).
- **Importing from arbitrary remote sources** (git repos, npm
  packages). All sources F14.10 supports are local filesystem paths.
