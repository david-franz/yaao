# F14.4 Help text & error message audit

**Phase**: 14 — Release Polish
**Priority**: Medium
**Dependencies**: F1.5

## Goal

Every command the user types — `yaao --help`, every subcommand `--help`, every `YaaoError` they can hit — gives them enough context to do the next right thing without grep-ing the source. Today coverage is patchy: some commands have terse one-line `Usage:` lines; some error paths have great hints (`YAAO_PLAN_UNTRACKED`); others throw bare messages that require reading source to decode.

## Scope: help text

A pre-v1 audit of `node dist/bin/yaao.js <cmd> --help` for every command surfaced these gaps:

| Command | Gap |
| --- | --- |
| `yaao` (top-level) | No worked example / common workflow pointer. Add a footer line: "Run `yaao <subcommand> --help` for any command, or see the README's Quickstart for a five-line walkthrough." |
| `yaao init` | The one-line description doesn't say what files are created. Expand to: `Initialize a yaao project — scaffolds .yaao/ (config, secrets template, plans/, exec/), updates .gitignore, and (default-on) registers yaao's MCP server in .mcp.json / per-agent equivalents.` |
| `yaao plan` | `--scope` says `feature \| project (auto-detected by default)` with no hint at what each means. Add: `feature = one plan file for a single feature in an existing codebase; project = multi-phase plan across many directories for green-field work.` |
| `yaao plan` | `--non-interactive` description is silent. Add: `never prompt for confirmation; suitable for CI/MCP-driven invocations.` |
| `yaao convert` | `--from auto` description buried in parens. Promote to its own line: `auto picks markdown vs speckit per-plan from the file shape (single .md → markdown; spec.md+plan.md+tasks.md → speckit).` |
| `yaao view` | Doesn't say this is a static render. Add a comparison: `Static one-shot render. For live progress, use \`yaao status --watch\`.` |
| `yaao run` | `--resume <run-id>` doesn't say where to find a runId. Add: `pass an existing runId (see \`yaao status\` for recent ones).` |
| `yaao stop` | One-liner is correct but says nothing about behaviour. Add: "Sends SIGTERM to the runner. The runner stamps `run:end status=cancelled` in the journal before exit. In-flight task branches are preserved (the work is not lost); the run can be resumed with `yaao run --resume RUNID`." Plus a hint about the omitted arg: "If no run-id is given, the most recent run with `status=running` is targeted." |
| `yaao serve` | One-line description doesn't say it's spawned by MCP clients. Add: `Spawned by MCP-aware editors (Claude Code, Cursor, Codex) via their MCP config. Not normally invoked by humans — use \`yaao web\` for browser-based inspection.` |
| `yaao web` | `--no-open` says "no-op in F13.0" — stale, it works now. Fix to: `don't auto-open a browser on start.` |
| `yaao agents` | Doesn't mention F14.1's doctor will absorb this. Add: `Subsumed by \`yaao doctor\` (Phase 14). Kept as a thin alias for scripts.` |

## Scope: error messages

Every `YaaoError` a new user can hit during `init` / `plan` / `convert` / `validate` / `run` / `stop` / `web` / `serve` carries a `hint:` that points at the fix. Today coverage is patchy — some paths have great hints (the plan-tracking gate, the secret-leakage rejection), others throw bare error messages that require reading source to decode.

### Process

1. Enumerate every `throw new YaaoError(...)` site in `src/`. Bucket by command path.
2. For each error, ask:
   - Can a user trigger it during a normal flow (i.e. is it an invariant or a real user-facing failure)?
   - If user-facing, does it tell them what to do next?
3. Add a `hint:` where it's missing. Strip stale hints where the workaround has been built into the engine (e.g. anywhere that says "run `yaao clean`" should now point at `yaao_prune`).

### Style guide for hints

- Imperative, second person: "run `X`", not "the user should run `X`".
- Reference real commands, not phases of work. ("run `yaao init`" not "complete project initialisation").
- One sentence max. Multi-step recoveries belong in a doc page the hint links to, not in the hint itself.
- Don't echo the error message. The hint adds *new* information.

### Specific call-outs

- `YAAO_AGENT_UNAVAILABLE` — currently says "the binary isn't on PATH"; should suggest `yaao doctor` (after F14.1 ships).
- `YAAO_PLAN_UNTRACKED` — already has a good hint; check the wording matches the new `--allow-untracked-plan` flag name.
- `YAAO_PLAN_API_NO_KEY` — should mention both `.yaao/secrets.local.json` *and* env vars; today it only mentions secrets.local.
- `YAAO_PLAN_NARROW_DAG` (commit 45bebdd) — already a warning not an error, but the wording is long; tighten.
- `YAAO_FEATURE_BRANCH_CREATE` (commit e181569) — has a good hint, audit consistency with the rest of the run-time errors.
- `YAAO_STOP_FAILED` (yaao_stop MCP tool, commit 8f7aded) — uses `result.hint` directly; make sure the underlying signalRun hints match the style guide.
- Web-server auth errors — should point at `--token` for non-loopback binds.

## Acceptance criteria

- Every command's `--help` output has a description that's at least one sentence beyond the bare verb.
- Every user-facing `YaaoError` instance carries a `hint:`.
- Every hint passes the four style-guide rules above (manual review).
- No hint references a CLI command or flag that doesn't exist.
- The help-audit table above is checked off (delete entries as they're addressed).

## Tests

- `tests/phase-14/help/snapshot.test.ts` — `yaao --help` + each subcommand's `--help` output snapshot-tested. The snapshots ARE the spec for what the user sees; any future change has to update them deliberately.
- `tests/phase-14/error-hints/coverage.test.ts` — walks the test corpus for every YaaoError code the codebase declares; asserts each produces a non-empty `hint` field in at least one test fixture. Coverage check, not behaviour check.
- Existing per-feature tests stay unchanged.

## Out of scope

- A typed error-code enum to replace string codes. Tempting but not the v1 hill to die on; the audit is the deliverable.
- Localisation of error / help messages.
- Embedded examples in every `--help`. The README quickstart (F14.3) covers the discovery story; in-command examples bloat the output.
