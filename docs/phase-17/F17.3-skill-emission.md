# F17.3 Skill Emission and Validation

**Phase**: 15 — Session → Skill Distillation
**Priority**: High
**Dependencies**: F17.1, F8.1 (skill format), F8.6 (`skills install`), [F12.6](../phase-12/F12.6-skill-hot-reload.md) (hot reload — delivers the watcher this section's step 6 relies on)

## Goal

Take the distiller's output (a draft `skill.yaml` + `prompt.md` pair plus a target directory), validate it through the existing F8.1 pipeline, write it to disk, and trigger the existing per-agent emitters so the new skill becomes invokable across all backends.

This is the integration seam between the distiller (F17.1) and the rest of yaao's skill machinery. It should add **zero new schema** and **zero new validation rules** — emission reuses F8.1 verbatim.

## Inputs

```typescript
interface EmissionRequest {
  /** Output skill metadata (parsed and Zod-validated against SkillMetadataSchema). */
  metadata: SkillMetadata;
  /** Skill prompt body. */
  prompt: string;
  /** Project (.yaao/skills/) or user (~/.yaao/skills/). */
  scope: 'project' | 'user';
  /** Project root (used for the project scope). */
  cwd: string;
  /** If true, run `skills install` after writing so per-agent files are emitted. */
  install?: boolean;
  /** If true, do not write — return the rendered files for inspection. */
  dryRun?: boolean;
}
```

## Output Layout

For metadata.name `add-api-endpoint`, scope `project`:

```text
.yaao/skills/add-api-endpoint/
├── skill.yaml
└── prompt.md
```

For scope `user`:

```text
~/.yaao/skills/add-api-endpoint/
├── skill.yaml
└── prompt.md
```

No `examples/` directory by default — the F17.1 prompt embeds its "Distillation notes" inline at the bottom of `prompt.md`, which is sufficient as a paper trail. An `examples/` subdir may be added later if users want it.

## Steps

1. **Validate metadata.** Parse `metadata` through `SkillMetadataSchema` ([format.ts:18](../../src/skills/format.ts#L18)). On failure, return a structured error with the Zod issues.
2. **Validate placeholders.** Run `validateSkill({ metadata, prompt, examples: [], origin: '<pending>' })` ([format.ts:135](../../src/skills/format.ts#L135)). The two existing checks both apply:
   - `YAAO_SKILL_UNREFERENCED_INPUT` — declared input that doesn't appear as a `{{placeholder}}` in the prompt.
   - `YAAO_SKILL_UNDECLARED_PLACEHOLDER` — `{{placeholder}}` in the prompt without a matching input.
   The 10 KB prompt-size limit is not waived; if the distilled prompt exceeds it, surface the warning and require an explicit `allowLarge: true` on the emission request (set by F17.4's MCP tool input).
3. **Resolve target directory.** Project scope: `<cwd>/.yaao/skills/<name>/`. User scope: `~/.yaao/skills/<name>/`. Refuse to overwrite an existing directory unless the request comes from F17.5 (refinement), which sets an explicit `merge: true` flag.
4. **Write atomically.** Write `skill.yaml` and `prompt.md` to a tmp dir, then rename into place. This avoids partial state if the process dies mid-write. If `dryRun: true`, skip this step and return the rendered content in the response.
5. **Trigger `skills install`** (if `install: true`). Reuse `skills install` from F8.6 — same code path the user would run manually. This is what makes the new skill available across Claude Code, Cursor, Copilot, Codex without further user action.
6. **Hot reload (MCP path).** When emission happens via `yaao_distill` (F17.4) and `yaao serve` is running, [F12.6](../phase-12/F12.6-skill-hot-reload.md)'s watcher picks up the new directory automatically and the SDK emits `tools/list_changed` on each registration. No explicit re-registration call is needed; calling agents see `yaao_skill_<name>` in the next tool-list round-trip.

## Validation Failure Modes

| Code | Cause | Response |
| --- | --- | --- |
| `YAAO_SKILL_METADATA_INVALID` | Zod failure on `skill.yaml` | Return the first issue path + message; do not write. |
| `YAAO_SKILL_UNREFERENCED_INPUT` | Input declared, no `{{x}}` in prompt | Return as `warnings[]`; offer `--strict` to upgrade to error. |
| `YAAO_SKILL_UNDECLARED_PLACEHOLDER` | `{{x}}` in prompt, no input | Hard error; do not write. (A placeholder with no input renders literally at runtime — almost always a distillation bug.) |
| `YAAO_SKILL_PROMPT_TOO_LARGE` | Prompt > 10 KB | Hard error unless the emission request sets `allowLarge: true`. |
| `YAAO_SKILL_EXISTS` | Target directory already exists, `merge: false` | Hard error; suggest the caller re-call with `refine: '<name>'` (F17.5) or a different name. |

## Output

```typescript
interface EmissionResult {
  ok: boolean;
  /** Files that were (or would be) written, absolute paths. */
  files: string[];
  /** Per-agent files written by `skills install`, if it ran. */
  installed?: { agent: string; files: string[] }[];
  warnings: { code: string; message: string }[];
  /** Populated when dryRun: true. */
  preview?: { 'skill.yaml': string; 'prompt.md': string };
}
```

## Why reuse `validateSkill` rather than a distiller-specific check

The whole point of emitting into the existing skill format is so the resulting artifact is indistinguishable from a hand-written one. Adding a parallel validator would create two ways for a skill to be "valid" and inevitably drift. The distiller's prompt (F17.1) is responsible for *producing* a skill that passes `validateSkill` — if it fails, the prompt is wrong, not the validator.

## Acceptance Criteria

- A valid `EmissionRequest` writes both files atomically to the correct scope directory.
- An invalid `skill.yaml` (Zod failure) returns a structured error without writing.
- An `{{undeclared}}` placeholder in the prompt is a hard error.
- A prompt > 10 KB is rejected unless the emission request sets `allowLarge: true`.
- `install: true` triggers per-agent emitters and lists what was written.
- `dryRun: true` returns the rendered content without touching the filesystem.
- `yaao serve` running in the background observes the new directory and emits `tools/list_changed` within ~1 s of write completion.
