# F17.4 `yaao_distill` MCP Tool

**Phase**: 15 — Session → Skill Distillation
**Priority**: High
**Dependencies**: F17.1, F17.2, F17.3, F12.1 (MCP server scaffold), [F12.6](../phase-12/F12.6-skill-hot-reload.md) (hot reload — required for the "callable in the next turn" UX below)

## Goal

A custom MCP tool that drives the full distillation pipeline end-to-end (validate session → run distiller → emit skill → install per-agent stubs), parallel in shape to `yaao_plan` (F12.2) and `yaao_convert` (F12.3). This is the **sole entry point** for Phase 17 — there is no shell-CLI equivalent. The rationale is in [PHASE-17.md](PHASE-17.md): distillation only makes sense in-context, so MCP is the only honest surface.

This is **not** the same as the auto-registered `yaao_skill_yaao-distiller` tool that F12.5 would otherwise produce. The auto-registered one returns the raw distiller prompt body for the calling agent to act on. `yaao_distill` is the **driver** tool that runs the whole pipeline and returns the written file paths. Same relationship `yaao_plan` has to the bare `yaao-planner` skill body.

## Schema

```json
{
  "name": "yaao_distill",
  "description": "Distill the calling agent's session into a reusable yaao skill, written to .yaao/skills/<name>/ and made available across all connected agents.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "name":         { "type": "string", "description": "Kebab-case slug for the new skill. If omitted, the distiller proposes one." },
      "description":  { "type": "string", "description": "One-line description of when the skill should be invoked." },
      "session":      { "type": "object", "description": "A SessionRecord (F17.2) — the calling agent's structured self-summary of its conversation. Required." },
      "scope":        { "type": "string", "enum": ["project", "user"], "default": "project" },
      "refine":       { "type": "string", "description": "Name of an existing skill to evolve (F17.5). Mutually exclusive with `name`." },
      "force":        { "type": "boolean", "default": false, "description": "Override the uncommitted-changes check on refinement (F17.5)." },
      "allowLarge":   { "type": "boolean", "default": false, "description": "Permit prompt bodies > 10 KB (F17.3)." },
      "install":      { "type": "boolean", "default": true, "description": "Re-emit per-agent stubs after writing." },
      "dryRun":       { "type": "boolean", "default": false }
    },
    "required": ["session"]
  }
}
```

`session` is required: yaao does not read any IDE-internal transcript store, so the caller must supply the `SessionRecord` payload. `name` is not required at the schema level because the distiller can propose one — but emission fails if neither `name` nor `refine` resolves to a slug.

## Output

The MCP `content[]` carries a human-readable summary suitable for the calling agent to show the user verbatim. The structured `result` carries the machine-usable payload:

```json
{
  "ok": true,
  "skill": {
    "name": "add-api-endpoint",
    "dir": ".yaao/skills/add-api-endpoint",
    "version": 1,
    "scope": "project",
    "inputs": [
      { "name": "resource", "required": true },
      { "name": "fields",   "required": true }
    ]
  },
  "installed": [
    { "agent": "claude-code", "files": [".claude/skills/add-api-endpoint/SKILL.md"] }
  ],
  "mcpTool": "yaao_skill_add-api-endpoint",
  "warnings": []
}
```

`mcpTool` tells the caller the auto-registered tool name so it can invoke the new skill immediately in the same session.

## How the agent populates `session`

In-session capture is the only supported mode (F17.2). The flow:

1. The agent, in some prior turn, decides (or is asked) to distill the current conversation into a skill.
2. The distiller's capture instruction — embedded in the skill body the agent reads at invocation time (F17.1) — tells the agent how to build a `SessionRecord`: ordered turns, tool calls, files touched, user corrections.
3. The agent assembles that record and calls `yaao_distill` with `session: <record>` and any optional metadata (`name`, `description`, `scope`, `refine`).
4. yaao validates the record against the F17.2 Zod schema, applies redaction, and runs the rest of the pipeline (Stage 2 generalization → emission).

This works on every supported agent because the only requirement is "can call an MCP tool with a JSON argument" — no IDE-internal access is needed.

## Progress Notifications

Long-running steps emit MCP progress at these milestones:

- `progress: 'validating session record'`
- `progress: 'running distiller (agent: claude-code, 8s)'`
- `progress: 'validating output'`
- `progress: 'writing .yaao/skills/<name>/'`
- `progress: 'installing per-agent stubs'`

**Note:** today's MCP tools (`yaao_plan`, `yaao_run`) emit progress only through an internal `onProgress` callback wired to the CLI reporter — *not* through MCP `notifications/progress`. Surfacing progress to MCP clients is its own piece of plumbing not yet shipped; this section is the spec for what F17.4 should land. If progress-via-MCP isn't ready when F17.4 ships, the milestones above are still emitted via the internal channel and surfaced in the response's `events: []` field after the call completes (synchronous fallback).

## Cancellation

The MCP server today does not handle `notifications/cancelled` — that's net-new infrastructure F17.4 needs to add, not something it inherits. Two pieces:

1. **Server-side handler.** Subscribe to `notifications/cancelled` for the in-flight tool call and mark a per-request `AbortSignal` as aborted.
2. **Pipeline plumbing.** The distiller's agent spawn (F17.1) already uses `backend.spawn` which threads an `AbortSignal` via the lifecycle; F17.4 passes the per-request signal in.

Behavior on abort:

- Before agent spawn → fail fast with `YAAO_DISTILL_CANCELLED`, no FS write.
- During agent spawn → kill the agent, return `YAAO_DISTILL_CANCELLED` with whatever partial output was captured (discarded; no skill written).
- After write but before `skills install` → the written skill is preserved; the response notes `installed: []` and explains. The user can re-run `yaao skills install` themselves.

If F17.4 ships without `notifications/cancelled` handling, calling agents simply can't cancel mid-distillation — they wait for it to complete or time out client-side. That's tolerable for v1 (distillation takes single-digit seconds), so cancellation can land as a follow-up rather than gating the phase.

## Hot Reload

[F12.6](../phase-12/F12.6-skill-hot-reload.md) is the prerequisite. Its watcher picks up the new directory after F17.4's atomic write, the SDK fires `tools/list_changed`, and the MCP client refreshes its tool catalog. The same session that called `yaao_distill` can then call `yaao_skill_<name>` in the next turn. **Without F12.6 this story doesn't work** — the static F12.5 registration runs only at server build, so a freshly-written skill would require a reconnect. F12.6 was landed specifically to unblock this UX.

## Concurrent Calls

If two `yaao_distill` calls run concurrently against the same target name, the second blocks on a file lock at the target directory and either succeeds (if the first's atomic rename hasn't happened) or fails with `YAAO_SKILL_EXISTS`. This is fine — concurrent distillations of the same skill are a user error, not a supported flow.

## Acceptance Criteria

- A simple end-to-end through MCP (using the fake-agent backend, with a hand-built `SessionRecord` argument) produces a written skill and returns the structured payload.
- Progress milestones are emitted (via MCP `notifications/progress` if the progress-over-MCP plumbing has landed; otherwise via the synchronous `events: []` fallback in the response).
- A call missing the `session` argument fails Zod input validation and returns an MCP error.
- An invalid `SessionRecord` (per F17.2's schema) returns an MCP error before the agent is spawned.
- After successful distillation, the new `yaao_skill_<name>` tool is callable in the same MCP session without a reconnect (delivered by [F12.6](../phase-12/F12.6-skill-hot-reload.md)).
- **If** cancellation support is in this drop: `notifications/cancelled` cleanly stops the agent and returns an MCP error; no half-written skill directory. If deferred to a follow-up: documented in the response shape so callers know cancellation is best-effort (client-side timeout).
