# F3.2 Dependency-Aware Branch Graph

**Phase**: 3 — Worktree & Git Engine
**Priority**: Critical
**Dependencies**: F2.1, F2.3

## Goal

Translate the plan's logical task DAG into the concrete branches each worktree should fork from and merge in. Downstream tasks must see their parents' committed work, not stale `main`.

## Inputs and Outputs

```typescript
// src/git/branch-graph.ts
export interface BranchPlan {
  byTask: Map<string, {
    branch: string;            // unique branch name for this task
    baseBranch: string;        // exactly one (the "primary" parent or base)
    parentBranches: string[];  // other parents to merge in (zero for linear DAGs)
  }>;
  baseBranch: string;          // overall base (e.g. "main")
}

export function planBranches(plan: ResolvedPlan): BranchPlan;
```

## Naming

Branch names default to `<plan.name>/<task.id>`. A task's `branch:` field overrides; the validator ensures uniqueness.

## Base / Parent Selection

For each task `T`:

- **No deps** → `baseBranch = plan.config.baseBranch`, `parentBranches = []`.
- **One dep `P`** → `baseBranch = branchOf(P)`, `parentBranches = []`.
- **Multiple deps** → choose a primary, merge the others in:
  - Primary is the dep with the **most transitive descendants** in the DAG (likeliest to be the "main line"); ties broken by lexicographic task ID.
  - `parentBranches = otherDeps`.

This heuristic minimizes the depth of merge commits and tends to produce intuitive branch lineage. It is documented and overridable via a per-task `primary-dep:` field (post-MVP).

## Why fork from a *parent's branch* rather than always merging?

Forking inherits history cleanly without the overhead of a merge commit. Merging is only needed when there's more than one parent. This matches `git`-native conventions and keeps the branch graph human-readable.

## Worktree Order

The branch graph also exposes a topological order (`Iterable<string>` of task IDs) used by the scheduler in Phase 5 and the merger in Phase 6.

## Acceptance Criteria

- Linear chain (`a → b → c`) produces `b` based on `a`, `c` based on `b`, no merges.
- Diamond (`a → b, a → c, b+c → d`) produces `d` based on whichever of `b`/`c` has more descendants (here equal — tie-break to `b` lexicographically), `parentBranches = [c]`.
- A task with `branch:` override uses the override.
- The function is pure (no IO).
