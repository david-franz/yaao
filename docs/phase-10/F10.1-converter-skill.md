# F10.1 yaao-converter Skill Design

**Phase**: 10 — yaao-converter Skill
**Priority**: Critical
**Dependencies**: F8.1, F2.1

## Goal

Define the `yaao-converter` skill: turn an implementation plan (yaao-authored or generic) into a deterministic, schema-validated execution plan in YAML.

## Skill Metadata

```yaml
name: yaao-converter
version: 1
description: Convert an implementation plan into an execution plan (YAML)
appliesTo:
  agents: [claude-code, cursor, copilot, codex, api]
tools:
  - read_file
  - write_file
  - list_files
  - context_query
inputs:
  - { name: input, required: true }              # path to the plan
  - { name: out, default: .yaao/exec/ }
  - { name: split, default: false }              # one file vs phase-split
trigger:
  manual: true
```

## Skill Behavior

The converter is *not* free-form. It is constrained to:
1. Read the input plan file(s).
2. Parse them deterministically — yaao supplies the parser via the F10.2 / F10.3 deterministic toolchain. The agent does NOT freelance parsing; it calls a `parse_plan` tool yaao exposes alongside the standard ones.
3. Map each task to an execution-plan task with explicit fields.
4. Infer `depends:` arrays (F10.4) — only when the source plan has explicit dependencies; the agent does not invent them.
5. Assign agents per heuristics (F10.5).
6. Emit YAML via a `write_plan` tool that schema-validates before writing. Invalid output is rejected and the agent must correct.

## Why use a skill instead of pure code?

Two reasons:
- Plan formats vary in human ways (the user's hand-edited plan, third-party formats, slight Spec Kit drift). An LLM is forgiving where a parser would fail.
- The skill can ask for clarification: when a task's prompt is ambiguous about its agent or dependencies, it can prompt the user (in the CLI driver) rather than guessing.

The deterministic parts (schema, dependency inference rules, default agents) live in code. The skill orchestrates and decides on ambiguity.

## Tool Surface (provided by yaao to the skill)

```typescript
parse_plan(path: string) → ParsedPlanIR     // F10.2 + F10.3 normalize both formats
write_plan(plan: ExecutionPlan, path: string)  // schema-validates first
ask_user(question: string) → string         // surfaces a prompt to the CLI driver
```

`ParsedPlanIR` is yaao's intermediate representation: tasks, prose, references, source positions. The skill works against this, not raw markdown.

## Output Determinism

For a given input, the converter should produce identical YAML across runs (modulo asks). Implementation: the skill is instructed to sort tasks topologically-then-lexicographically, choose default agents from a fixed lookup, and never inject creative reformatting.

## Acceptance Criteria

- Skill validates against F8.1.
- Emits to all agent formats.
- A test corpus of 10 reference plans converts successfully under fake-agent transcripts; outputs schema-validate.
- Round-trip stability: convert → run → convert again on a slightly modified plan → diff is small and explicable.
