# F10.6 `yaao convert` Command

**Phase**: 10 — yaao-converter Skill
**Priority**: Critical
**Dependencies**: F10.1 - F10.5

## Goal

The CLI driver for the converter. Loads the input plan, resolves the converter skill, runs the agent against the deterministic IR, writes validated YAML.

## CLI

```
yaao convert <plan> \
  [--out <path>] \
  [--split] \
  [--from markdown|speckit|auto] \
  [--infer-deps off|suggest|auto] \
  [--apply-inferred] \
  [--agent <name>] \
  [--model <name>] \
  [--dry-run] \
  [--non-interactive]
```

Defaults:
- `--from auto` — detects format (file extension + content sniff).
- `--out` — `.yaao/exec/<plan-slug>.yaml` (or directory if `--split`).
- `--infer-deps off`.

## Steps

1. Resolve the input file (or directory for project-scope or speckit).
2. Run the format detector → markdown / speckit.
3. Run the appropriate parser (F10.2 or F10.3) to produce IR.
4. Resolve the converter skill, agent, ctx-sys (same flow as `yaao plan`).
5. Spawn the agent. The agent uses `parse_plan`, `infer_deps` (when enabled), `ask_user` (when ambiguous), and `write_plan`.
6. The skill calls `write_plan(plan, path)`. yaao schema-validates and either writes or rejects with feedback to the agent.
7. After success, run F2.3 DAG validation on the produced plan; warnings are printed (not blocking).

## Split Mode

`--split`: emit one execution plan per source phase, plus a top-level plan with `includes:` references:

```
.yaao/exec/<slug>/
├── plan.yaml                # top-level with includes
├── 01-foundation.yaml
├── 02-api.yaml
└── 03-tests.yaml
```

The top-level plan's tasks are empty; its `includes:` reference each phase. Cross-phase dependencies become `depends:` on tasks in the lower-level files.

## ask_user Behavior

When the converter skill calls `ask_user(question)`:
- Interactive TTY: yaao prints the question and reads stdin.
- `--non-interactive`: yaao returns "skip" and the skill must produce a best-effort answer or fail with a clear "ambiguity unresolvable" error.

## Auto-validation

After write, yaao runs the F2.3 validator. Issues are printed; user can fix the YAML manually or re-run with edits to the source plan.

## Output

```
$ yaao convert .yaao/plans/oauth.md
✔ converted plan
  source: .yaao/plans/oauth.md         (9 tasks)
  output: .yaao/exec/oauth.yaml         (9 tasks, 3 layers)
  agents: claude-code(7), cursor(1), codex(1)
  warnings: 1 (YAAO_PLAN_FAN_OUT_HIGH on layer 2)

next:
  yaao validate .yaao/exec/oauth.yaml
  yaao run .yaao/exec/oauth.yaml
```

## Acceptance Criteria

- Round-trip: a yaao-emitted plan converts to a valid execution plan that validates and dry-runs cleanly.
- A Spec Kit triplet converts equivalently.
- A hand-authored loose plan converts with sensible defaults and warnings about anything inferred.
- `--split` emits a working multi-file plan that yaao loads as a single resolved plan.
