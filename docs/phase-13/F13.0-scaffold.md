# F13.0 Web Viewer Scaffold

**Phase**: 13 — Web Viewer
**Priority**: High
**Dependencies**: F12.1 (existing MCP server scaffold to mirror), F12.6 (FS watcher pattern to reuse)

## Goal

Land the structural foundation the rest of Phase 13 builds on, before any feature work. Everything F13.1 onwards assumes a server process under `yaao web`, an HTTP+SSE listener wired up, a frontend build pipeline emitting to `dist/web/`, and an end-to-end "browser loads a page served by the binary" smoke test. F13.0 ships exactly that — empty pages, no feature surface — so the F13.1-F13.6 work can land incrementally without rebuilding the seams every PR.

This is also the right place to make the dependency and packaging decisions that affect every later feature (`hono` vs alternative, the `web/` package layout, the dist-build pipeline), so they're made once with the small footprint of a hello-world, not amid a feature PR.

## What "scaffold" means in this phase

Six concrete pieces, each minimal:

1. **`yaao web` CLI command.** New subcommand registered the same way as `yaao serve`. Defaults: `--host 127.0.0.1`, `--port 0` (kernel-assigned), `--no-open` available. Prints the bound URL on startup. Does not yet expose any tool surface — that's F13.1's job. Just brings the listener up and serves a hello page.
2. **HTTP server.** [`hono`](https://hono.dev/) on the Node `@hono/node-server` adapter — small, ESM-native, ships well in a CLI. Single route at this stage: `GET /` returns a placeholder HTML page that says "yaao web — wired up". A `GET /api/health` returns a stub `{ ok: true, version }` so the bundle integrity tests have something to hit.
3. **Static asset serving.** The CLI binary embeds the built frontend bundle from `dist/web/`. The hono route resolves bundle paths relative to the package's installed location (`new URL('../dist/web/index.html', import.meta.url)`), not the user's `cwd`. Path-traversal-safe.
4. **Frontend package layout.** A separate `web/` subdirectory with its own `package.json` (`yaao-web` internal name), `vite.config.ts`, `tsconfig.json`, a single `index.html` + `src/main.tsx` that renders "yaao web — wired up". This keeps the root package.json's deps focused on the engine; React / Vite / Monaco live in `web/`.
5. **Build wiring.** Root `npm run build` runs the existing `tsup` build, then runs `npm --workspace web run build` (or equivalent), then copies `web/dist/` into `dist/web/`. The yaao binary always finds `dist/web/index.html` at the same relative path regardless of how it was installed.
6. **End-to-end smoke test.** A vitest test starts `yaao web` on `127.0.0.1:0`, reads the bound port from stdout, fetches `GET /` + `GET /api/health`, asserts the responses. Tears the server down on completion. This is what proves the wiring works before any feature relies on it.

## Decisions to lock in

A few package-shape choices that affect every later F13 feature:

- **Monorepo vs single package?** Single package with a `web/` subdir as a workspace. npm workspaces are simpler than a separate package, and the frontend is genuinely co-evolved with the server. `package.json` gains a `"workspaces": ["web"]` field.
- **HTTP framework: hono.** Small, ESM-native, fast, ships well from `dist/`. Alternatives considered: Fastify (heavier startup, ESM is awkward), bare Node http (too low-level for SSE replay + auth). `hono` is the pick; pinned at install time.
- **Frontend build: Vite.** Industry-standard for React + TypeScript, fast HMR for dev, produces a single static bundle. Monaco's Vite plugin (`vite-plugin-monaco-editor`) handles worker chunking automatically for the editors landing in F13.5 / F13.6.
- **Where bundled assets live.** `dist/web/index.html` + assets. The yaao bin (`dist/bin/yaao.js`) resolves them relative to its own `import.meta.url` so global installs work.
- **Static-only in `dist`.** The frontend bundle is fully static — no server-side render, no per-user state baked in. All dynamic state arrives via the `/api/*` endpoints landing in F13.1.
- **No auth in F13.0.** The token-required-for-non-loopback rule lives in F13.1's `Auth` section. F13.0 only binds loopback.
- **TypeScript everywhere.** Both `src/` and `web/src/` are TypeScript. The two TypeScript projects do NOT share a `tsconfig.json` — `web/tsconfig.json` extends the root but overrides JSX + lib for browser targets.

## Out of scope (lands in later F13.x)

- Any `/api/*` route besides `/api/health`. F13.1 ships them.
- React routing or the DAG component. F13.2.
- Live run view, SSE stream, activity stream. F13.3.
- Workspace page, plan editor, config editor. F13.4-F13.6.
- Browser-side state management beyond what `index.html` + `main.tsx` need to render. Picking Zustand vs alternatives is F13.2's call.
- Auth tokens. F13.1.

## Acceptance criteria

- `yaao web` starts a server on a kernel-assigned port and prints the URL.
- `GET /` returns an HTML page with a body that mentions "yaao web" (so the smoke test has a literal string to grep).
- `GET /api/health` returns 200 with JSON `{ ok: true, version: <yaao version> }`.
- `npm run build` produces both the engine (`dist/bin/yaao.js`, `dist/index.js`) and the frontend (`dist/web/index.html` + bundled assets) from a single root command.
- `dist/web/` is included in the npm `files` array so global installs ship the bundle.
- The smoke test in `tests/phase-13/scaffold/` passes.
- `yaao serve` (the MCP stdio server) is untouched — F13.0 is purely additive.

## Tests

- `tests/phase-13/scaffold/yaao-web-starts.test.ts` — spawn the binary on `127.0.0.1:0`, read the port, fetch `/`, assert status 200 + body contains "yaao web".
- `tests/phase-13/scaffold/api-health.test.ts` — same harness, fetch `/api/health`, assert `{ ok: true, version }` shape.
- `tests/phase-13/scaffold/static-bundle-served.test.ts` — verify a bundled asset (e.g. the favicon, the `/assets/index-*.js` chunk) is reachable.
- `tests/phase-13/scaffold/build-pipeline.test.ts` — after `npm run build`, assert `dist/web/index.html` exists and the script tags point at chunks that also exist in `dist/web/assets/`.

## Why a dedicated scaffold step

F13.1's spec is large and assumes the server + bundle pipeline are already there. Folding F13.0 into F13.1 would mean the first PR has to land the framework choice, the build pipeline, the new directory structure, AND the API surface — too much for one review. Splitting the scaffold off means the framework and packaging decisions get their own focused review, and F13.1 onwards land against a stable foundation.
