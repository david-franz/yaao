# F12.4 `yaao_run` & `yaao_status` MCP Tools

**Phase**: 12 — yaao-as-MCP
**Priority**: Medium
**Dependencies**: F12.1, F5.4, F11.5

## Goal

Expose `yaao run` and `yaao status` as MCP tools. Long-running runs use progress notifications and an asynchronous result pattern: `yaao_run` returns a `runId` immediately; the parent polls or subscribes via `yaao_status`.

## `yaao_run` Schema

```json
{
  "name": "yaao_run",
  "description": "Start an execution plan run.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "plan":         { "type": "string" },
      "maxParallel":  { "type": "number" },
      "only":         { "type": "array", "items": { "type": "string" } },
      "skip":         { "type": "array", "items": { "type": "string" } },
      "resume":       { "type": "string", "description": "run-id to resume" },
      "dryRun":       { "type": "boolean", "default": false }
    },
    "required": ["plan"]
  }
}
```

## `yaao_run` Output

```json
{
  "ok": true,
  "runId": "a3f1k",
  "tasks": 9,
  "layers": 3,
  "estimatedParallelism": 4
}
```

The run continues in the background of the MCP server. Progress notifications stream:

- `task:active` — `{ taskId, agent, model, branch }`
- `task:completed` — `{ taskId, durationMs, filesChanged }`
- `task:failed` — `{ taskId, error: { code, message } }`
- `run:end` — `{ status, durationMs }`

## `yaao_status` Schema

```json
{
  "name": "yaao_status",
  "description": "Inspect a run by ID (or the latest run).",
  "inputSchema": {
    "type": "object",
    "properties": {
      "runId": { "type": "string" },
      "task":  { "type": "string" },
      "watch": { "type": "boolean", "default": false }
    }
  }
}
```

## `yaao_status` Output

Returns a `RunSummary` (F3.4). When `watch: true`, the tool keeps the call open and emits MCP progress notifications until the run ends.

When `task` is set, the result also includes the recent log tail for that task.

## Lifecycle

- Multiple concurrent `yaao_run` invocations on the same MCP server are serialized: the second one waits for the first to release the project lock. The MCP server reports queued status via `notifications/progress`.
- Cancellation via MCP `notifications/cancelled` cancels the run (graceful shutdown).

## Backgrounding

A parent that doesn't want to keep the MCP call open can pass `background: true`. The call returns immediately with the run-id and the parent uses `yaao_status` later. (Default is to keep the call open until `run:end`.)

## Acceptance Criteria

- `yaao_run` over MCP produces the same outcome as `yaao run` from the CLI for the same plan.
- Progress notifications fire in order; the parent can reconstruct the run from them.
- `yaao_status` on a finished run returns the journal-derived summary even after the server restarts.
- Cancellation is honored.
