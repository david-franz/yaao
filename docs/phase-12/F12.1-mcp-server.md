# F12.1 yaao MCP Server Scaffold

**Phase**: 12 — yaao-as-MCP (primary integration surface)
**Priority**: Critical
**Dependencies**: F1.3, F5.4, F9.5, F10.6

## Goal

Expose yaao itself as an MCP server. **This is the primary way every supported agent — Claude Code, Cursor, Copilot, Codex, raw API — drives yaao.** Build alongside Phase 8: the skills emitters (F8.2-F8.5) emit MCP-config bootstraps that point at this server. Build F12.1 first; F12.5 is also load-bearing for Phase 8.

## Transport

```
yaao serve [--stdio | --socket <path>] [--http <addr>]
```

- `--stdio` (default): MCP over stdin/stdout. The standard for embedding into a parent agent.
- `--socket <path>`: Unix domain socket for long-lived attachments.
- `--http <addr>`: HTTP transport (for the web viewer; F14).

## Server Implementation

Built on `@modelcontextprotocol/sdk`'s server.

```typescript
// src/mcp/server.ts
export async function serve(opts: ServeOptions): Promise<void> {
  const server = new Server({ name: 'yaao', version: VERSION });
  registerTool(server, yaaoPlanTool);       // F12.2
  registerTool(server, yaaoConvertTool);    // F12.3
  registerTool(server, yaaoRunTool);        // F12.4
  registerTool(server, yaaoStatusTool);     // F12.4
  registerTool(server, yaaoValidateTool);
  registerTool(server, yaaoAgentsTool);
  registerTool(server, yaaoPlansTool);
  registerSkillTools(server);               // F12.5 — auto-register every .yaao/skills/<name>/ as yaao_skill_<name>
  await server.connect(makeTransport(opts));
}
```

## Tool Registration

Each tool has:

- A name. Built-in tools are namespaced `yaao_*` (`yaao_plan`, `yaao_convert`, `yaao_run`, …). User skills are `yaao_skill_<name>`.
- A JSON Schema for inputs (derived from the F2.1 / F1.3 Zod schemas, or from `skill.yaml.inputs` for skill tools).
- A handler that routes into the same code paths the CLI uses.

## Lifecycle / Concurrency

- One yaao MCP server per project.
- The server holds a single project context (config + cwd). Multi-project hosting is out of scope for v1.
- Long-running tools (`run_plan`) use MCP progress notifications for streaming updates.
- **Concurrent invocations are NOT serialized.** The pre-v1 doc here claimed the server queued `run_plan` calls behind a `.yaao/.lock`; that lock never existed in `src/` and (per F16.2) is deliberately not added — the workflow yaao wants to support is *concurrent runs against distinct feature branches*, not queued runs. Isolation comes from runId entropy (F16.1), per-runId worktree paths, atomic git ref CAS on merge targets, and the per-run journal directory. See [phase-16/F16.2-concurrency-model.md](../phase-16/F16.2-concurrency-model.md) for the documented invariants.

## Authentication

- Stdio: trust the parent process.
- Socket: trust local FS permissions.
- HTTP: bind only to `127.0.0.1` by default; require a token (`yaao serve --http :PORT --token <t>`) for non-loopback binds.

## Error Surface

MCP tool errors map yaao's `YaaoError` codes into MCP error codes. The error message and hint are surfaced verbatim.

## Acceptance Criteria

- A simple MCP client connects via stdio, calls `tools/list`, and gets the expected toolset.
- The server serializes input validation errors in MCP format with `code` and message.
- Killing the parent process cleanly shuts down the server (no orphaned ctx-sys subprocesses).
