# F12.6 Skill Hot Reload

**Phase**: 12 — yaao-as-MCP (primary integration surface)
**Priority**: High
**Dependencies**: F12.5
**Status**: Shipped — [src/mcp/skill-watcher.ts](../../src/mcp/skill-watcher.ts), wired into `buildMcpServer` + `serve()` in [src/mcp/server.ts](../../src/mcp/server.ts).

## Goal

Keep the MCP server's tool catalog in sync with the on-disk skill set while a session is live. F12.5 auto-registers every skill at server-build time; without F12.6 a freshly-written skill — manually placed or distilled by F13 — wasn't callable until `yaao serve` restarted. That broke the "land a skill, invoke it in the next turn" UX that F12.5 implied.

## Watched roots

Two locations, in this order of precedence (same resolver as F8.1 / `listSkillDirs`):

1. `<cwd>/.yaao/skills/` (project)
2. `~/.yaao/skills/` (user)

Built-in skills (`src/skills/builtin/`) are **not** watched. They ship with the binary, can't change at runtime, and watching the source tree would pin the runtime to a working copy.

## Mechanism

`createSkillWatcher` in [src/mcp/skill-watcher.ts](../../src/mcp/skill-watcher.ts) wraps native `fs.watch(dir, { recursive: true })` over each root. `recursive: true` is supported on macOS / Windows from Node ≥ 14 and on Linux from Node ≥ 20 — `engines.node` already requires ≥ 20, so no new dependency is needed.

A 250 ms debounce coalesces the multi-event burst that atomic-rename writes (F14.3) produce. The window is long enough to swallow noise, short enough to feel instant from a client's perspective.

On each fire, the server calls `reconcileSkillTools(server)` which:

1. Runs `discoverSkills(ctx)` to get the live skill set.
2. Diffs against the server's currently-registered skill tools (tracked in a per-server `Map<name, RegisteredHandle>`).
3. For each new skill → calls `server.registerTool(...)`. The MCP SDK fires `notifications/tools/list_changed` automatically on each registration.
4. For each disappeared skill → calls `handle.remove()` (which the SDK exposes as `update({ name: null })`). Same auto-fire.

`tools/list_changed` is what MCP clients listen for to refresh their tool catalog. Cursor, Claude Code, and Codex all support it; older Copilot may need a reconnect. The notification is the contract — yaao does nothing else to advertise the change.

## Failure modes

- **Watch root doesn't exist** — the watcher tolerates a missing directory (skill roots are optional). When the directory appears later, callers re-invoking `startSkillWatcher` (or simply restarting) pick it up. The 95% case is `~/.yaao/skills/` being absent on a fresh project, which is fine.
- **`EMFILE` / `EACCES`** — `fs.watch` may surface these as async `error` events. The watcher demotes them to no-ops so a noisy file system doesn't take down the host process. Discovery falls back to the existing static scan on the next server build.
- **A malformed skill appears** — `discoverSkills` already silently skips skills that fail `validateSkill` (see [tools.ts:858](../../src/mcp/tools.ts#L858)). The reconciler treats them as absent. Fixing the skill's `skill.yaml` and saving again triggers another fire; the now-valid skill registers normally.

## Public API

```typescript
// in src/mcp/server.ts

/**
 * Reconcile the server's registered skill tools against what's currently on
 * disk. Adds tools for new skills, removes tools for skills that vanished,
 * leaves stable ones alone. Exposed for tests and for callers that mutate
 * skills programmatically without going through the FS.
 */
export function reconcileSkillTools(server: McpServer): { added: string[]; removed: string[] };

export interface StartSkillWatcherOptions {
  cwd: string;
  /** Debounce window in ms. Default 250. Tests use ~10 for snappier asserts. */
  debounceMs?: number;
  /** Skip ~/.yaao/skills/ — tests use this to keep the host's real home untouched. */
  skipUser?: boolean;
}

/**
 * Start watching skill roots and reconcile on change. Returns a handle whose
 * `.stop()` releases the underlying fs.watch fd. `serve()` wires this into
 * the transport-close path automatically.
 */
export function startSkillWatcher(server: McpServer, opts: StartSkillWatcherOptions): SkillWatcher;
```

## Concurrent calls

The reconciler is synchronous from JS's perspective; two FS events within the debounce window fire one reconcile pass. If two reconcile passes overlap (e.g. a long-running `discoverSkills` on a large user skill tree), the handle map is the single source of truth — duplicate registrations are guarded by the SDK's "tool already registered" error, which the reconciler catches and ignores.

## Acceptance criteria

- A new skill written under `<cwd>/.yaao/skills/<name>/` is registered as `yaao_skill_<name>` within ~250 ms (one debounce window), without restarting `yaao serve`.
- Removing a skill directory deregisters its tool within the same window; `tools/list_changed` is sent.
- The watcher tolerates a missing skill root and does not crash when one appears later.
- `serve()` cleans up the watcher's fd handles on transport close.
