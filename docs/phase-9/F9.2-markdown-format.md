# F9.2 Markdown Plan Format

**Phase**: 9 — yaao-planner Skill
**Priority**: Critical
**Dependencies**: F9.1

## Goal

Pin down the exact markdown convention yaao-planner emits and yaao-converter parses, so the round trip is lossless.

## File Naming

- Single-file feature plans: `.yaao/plans/<slug>.md`.
- Multi-file project plans: `.yaao/plans/<slug>/`
  - `00-overview.md`
  - `01-<phase-slug>.md`
  - `02-<phase-slug>.md`
  - …

## Document Skeleton (single file)

```markdown
# <Plan Title>

> <one-paragraph description>

## Metadata

- name: <plan-slug>
- scope: feature
- created: 2026-05-08
- ctx-sys: true

## Tasks

| id        | title                | depends      | agent (suggested) | model (suggested) |
|-----------|----------------------|--------------|-------------------|-------------------|
| scaffold  | Scaffold project     |              | claude-code       | opus              |
| api       | REST API             | scaffold     | claude-code       |                   |
| ui        | UI                   | scaffold     | cursor            |                   |
| tests     | E2E tests            | api, ui      | codex             |                   |

## scaffold — Scaffold project

<prose: what to do, why, file paths, constraints>

### Files
- package.json (added)
- tsconfig.json (added)
- src/index.ts (added)

### Validation
- `npx tsc --noEmit`
- `npm test`

## api — REST API

<prose>

### Files
- src/routes/*.ts
- src/server.ts

## ui — UI
...
```

## Multi-file Project Skeleton

`00-overview.md` lists phases:

```markdown
# <Project Title>

> <description>

## Metadata

- name: <slug>
- scope: project
- ctx-sys: true

## Phases

1. [Foundation](./01-foundation.md)
2. [API](./02-api.md)
3. [UI](./03-ui.md)
4. [Tests](./04-tests.md)
```

Each phase file has the same shape as a single-file plan, *plus*:
- A frontmatter-style block listing cross-phase dependencies:
  ```markdown
  ## Cross-phase dependencies
  - depends-on-phases: [01-foundation]
  ```

## Conventions

- Task IDs are unique **across the whole plan**, not per phase.
- Headings `## <id> — <title>` are how the parser locates tasks.
- The `Tasks` table is authoritative for `id`, `depends`, suggested agent/model.
- Prose under each task heading becomes the task's prompt body when converted.
- `### Files` is advisory — fed to the agent's context but not enforced.
- `### Validation` becomes `task.validation.command` when the converter recognizes a single-line shell command.

## Why a Table *and* Headings?

Redundancy is intentional: the table is easy for humans to scan and edit; the headings let prose live where it belongs. The parser cross-checks both — disagreements (e.g. table mentions task `foo` but no `## foo` heading) are reported.

## Acceptance Criteria

- A round-trip — emit, parse, re-emit — produces semantically equivalent output.
- The format is documented with a worked example committed under `examples/plans/`.
- Tasks discovered in headings but missing from the table → warning.
- Tasks in the table missing headings → error.
