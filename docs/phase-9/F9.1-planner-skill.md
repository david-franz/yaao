# F9.1 yaao-planner Skill Design

**Phase**: 9 — yaao-planner Skill
**Priority**: Critical
**Dependencies**: F8.1, F7

## Goal

Define the `yaao-planner` skill — the prompt body, system instructions, tools, and guardrails that turn a description into an implementation plan.

## Skill Metadata (`skill.yaml`)

```yaml
name: yaao-planner
version: 1
description: Generate an implementation plan from a description
appliesTo:
  agents: [claude-code, cursor, copilot, codex, api]
tools:
  - read_file
  - write_file
  - list_files
  - context_query        # ctx-sys, when present
inputs:
  - { name: description, required: true }
  - { name: scope, default: feature }       # feature | project
  - { name: format, default: markdown }     # markdown | speckit | both
  - { name: out, default: .yaao/plans/ }
trigger:
  manual: true
```

## Prompt Structure (`prompt.md`)

The skill's prompt has four sections:

1. **System** — role, output format, hard constraints.
2. **Process** — step-by-step procedure the model must follow.
3. **Output template** — the exact markdown shape (or Spec Kit triplet).
4. **Constraints** — non-negotiable rules.

### System

```
You are yaao-planner. You produce implementation plans for software work.
Your output is consumed downstream by yaao-converter, which turns it into a
machine-runnable execution plan.

You MUST:
- Output a plan that conforms to the format specified by `{{format}}`.
- Number every task within a phase, e.g. "1.1", "1.2".
- For each task, include: id (slug), title, a 1-3 sentence prompt, and `depends:` (list of task ids it depends on, or empty).
- Ensure dependencies form a DAG (no cycles).

You MAY:
- Use the `context_query` tool to learn about the existing codebase.
- Read files in the project to inform your plan.
- Suggest agent assignments per task (e.g., "this task suits Claude Code").

You MUST NOT:
- Write any code other than the plan file(s).
- Recommend tasks outside the project's directory.
- Output anything besides the plan file content (no commentary, no preamble).
```

### Process

```
1. If ctx-sys is enabled, call `context_query` for the description and a few
   refinements ("how is X currently implemented?", "what files relate to Y?").
2. Decide scope: `feature` produces a single plan file; `project` produces a
   multi-phase plan with one file per phase.
3. Decompose the work into phases (project) or task list (feature).
4. For each task: id, title, prompt, depends, suggested agent (optional).
5. Write the file(s) to `{{out}}` and print only the path(s) on stdout.
```

### Output template (markdown)

```markdown
# <plan title>

> <one-paragraph description>

## Tasks

| id          | title                       | depends    | agent (suggested) |
|-------------|-----------------------------|------------|-------------------|
| scaffold    | Scaffold the project        |            | claude-code       |
| api         | Implement the REST API      | scaffold   | claude-code       |
| ui          | Implement the UI            | scaffold   | cursor            |
| tests       | End-to-end tests            | api, ui    | codex             |

## scaffold — Scaffold the project

<2-5 sentences describing what to build, with file paths if known>

## api — ...
```

### Constraints

```
- Tasks must have unique ids matching `[a-z][a-z0-9-_]*`.
- The total number of tasks in a `feature` plan should be 3-12.
- The total number of tasks in a `project` plan should be capped at 60 across
  all phases; if more, split further phases out into separate files.
- Do not invent dependencies — only declare a dep if the task literally
  cannot start until the other completes.
```

## Why prescribe so heavily?

The skill's output is parsed by `yaao-converter` (F10). A loose, free-form plan would force the converter to do too much guessing. By pinning the format, conversion becomes deterministic.

## Acceptance Criteria

- Skill validates against F8.1.
- Emits to all four agent formats via Phase 8 emitters.
- A test plan ("add OAuth2 login") yields a parsable, valid plan from each backend in CI (using recorded transcripts).
