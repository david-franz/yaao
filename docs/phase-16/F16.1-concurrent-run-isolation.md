# F16.1 Concurrent-Run Isolation Hardening

**Phase**: 15 — Concurrent Runs & Context Handoff
**Priority**: High
**Dependencies**: F3.1 (worktree manager), F5.4 (runner), F3.4 (run journal)

## Goal

Make "two `yaao run`s of the same plan against two different feature branches,
started in the same tick, both complete cleanly" a documented, tested
guarantee. Today the engine *almost* supports this — worktrees are isolated
by runId on disk, merges use plumbing + atomic ref CAS — but two naming
choices cause collisions:

1. **runId is generated from `Date.now().toString(36)`** ([src/cli/commands/run.ts:115](../../src/cli/commands/run.ts#L115),
   [src/mcp/tools.ts:303](../../src/mcp/tools.ts#L303)). Millisecond
   resolution. Two MCP-driven `yaao_run` calls fired in the same tick get
   the same id and trample each other's journal + worktree paths.
2. **Default task branch is `${plan.name}/${task.id}`** ([src/plan/schema/resolve.ts:98](../../src/plan/schema/resolve.ts#L98)).
   No runId, no featureBranch. Two concurrent runs of the same plan both try
   to `git branch oauth/api` — the second fails with
   `WorktreeError: branch already exists`.

Both are one-line behaviour fixes; the work is the careful threading of the
new naming through the pieces that already key off branch names.

## Design

### runId entropy

Change `runId` to `run-${Date.now().toString(36)}-${nanoid(6)}` everywhere
it's generated. `nanoid` is already a dependency (it's used by the journal —
see [package.json](../../package.json) and
[src/git/journal.ts](../../src/git/journal.ts)). 6 alphanumeric characters
give ~10⁹ values per millisecond — enough collision-resistance that we can
drop the millisecond-based ordering assumption nothing relied on anyway.

Sites to change:

- `src/cli/commands/run.ts` (the `--resume <id>` fallback)
- `src/mcp/tools.ts` (the `yaao_run` tool handler)

The runId remains a stable string that's safe in file paths (no path
separators, no surprising shell characters). Existing journals on disk are
already keyed by the old shape and stay readable — this is a forward-only
change.

### Default branch namespacing

Change the default-branch derivation in `src/plan/schema/resolve.ts:98`:

```ts
// before
const branch = t.branch ?? `${plan.plan.name}/${t.id}`;

// after
const featureBranch = plan.plan.featureBranch;
const branch = t.branch ?? (featureBranch
  ? `${featureBranch}/${t.id}`
  : `${plan.plan.name}/${t.id}`);
```

Rationale: when the user sets `plan.featureBranch: feature/oauth`, every
task's default branch lives under that integration branch's namespace
(`feature/oauth/api`, `feature/oauth/ui`). Two concurrent runs against
*different* feature branches (`feature/oauth` and `feature/billing`) now
have disjoint task-branch namespaces by construction. The previous
behaviour — bare `<plan-name>/<task-id>` — collided whenever the user ran
the same plan twice in parallel.

Tasks with an explicit `branch:` field are unaffected; the user opted out
of the default scheme and we don't touch their choice.

**Note on cross-plan collisions:** when two plans share a `plan.name` but
have no `featureBranch`, the old collision risk remains. The workspace
default (next paragraph) catches the common case; users with two plans
sharing a name and no feature branch should set a `featureBranch` on at
least one or override `branch:` per task.

### Workspace-level safety net

Optional follow-up — not required to ship F16.1 but worth grouping here:
add a workspace config flag `defaults.branch-namespace: 'feature-or-plan'`
(default) or `'feature-or-run'`. The latter falls back to
`${plan.name}/${runId-prefix}/<task-id>` when no featureBranch is set, so
even two no-featureBranch runs of the same plan don't collide. Tradeoff:
branch names get longer and `yaao clean` has to know how to recognise
run-id-prefixed branches.

Recommendation: **ship just `'feature-or-plan'`** (the change above) for
F16.1. The runId-prefixed scheme is a v2 idea once a real user reports
needing it.

## Acceptance criteria

- `runId` collisions: two `runPlan({...})` calls invoked in the same tick
  against distinct featureBranches produce two distinct runIds.
- Branch namespacing: a plan with `plan.featureBranch: feature/foo` produces
  default task branches `feature/foo/<task-id>` (verified via
  `resolvePlan(...).tasks[*].branch`).
- A plan **without** `featureBranch` keeps the historical `${plan.name}/<task-id>`
  shape — backward-compatible.
- An integration test runs the same plan twice in parallel against two
  different featureBranches; both runs succeed end-to-end, both produce
  distinct merge commits on their respective integration branches, and the
  user's checked-out branch at the repo root is untouched.
- Existing tests that assert default branch names (`<plan-name>/<task-id>`)
  pass unchanged because they don't set `featureBranch`. Add coverage for
  the new branch shape under `tests/phase-16/`.

## Tests

- `tests/phase-16/run-id/entropy.test.ts` — two runId generations in the
  same tick differ.
- `tests/phase-16/branch-namespace/with-feature-branch.test.ts` —
  `resolvePlan` puts task default branches under `featureBranch`.
- `tests/phase-16/branch-namespace/without-feature-branch.test.ts` —
  legacy shape preserved.
- `tests/phase-16/branch-namespace/explicit-branch-override.test.ts` —
  per-task `branch:` field bypasses the namespace.
- `tests/phase-16/branch-namespace/branch-graph-base.test.ts` — when a
  layer-0 task's `baseBranch` is the featureBranch (the existing F3.2
  behaviour), the task's *own* branch is `featureBranch/<task-id>`. Sanity
  check that the two pieces compose.

## Out of scope

- Cross-plan branch collisions when two plans share `plan.name` and neither
  sets `featureBranch`. The workspace-level fallback above handles this in
  v2.
- Backfilling old journals with longer runIds. The change is forward-only;
  `--resume <oldRunId>` keeps working.
- Renaming the on-disk worktree directory shape. The runId is the path
  segment and the new shape is just longer — no migration needed.
