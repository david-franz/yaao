# F16.2 Concurrency Model — Docs Alignment + Integration Tests

**Phase**: 15 — Concurrent Runs & Context Handoff
**Priority**: High
**Dependencies**: F16.1

## Goal

Codify "yaao supports multiple concurrent runs against distinct feature
branches" as a tested, documented guarantee. Today the engine already
behaves correctly for this workflow (after F16.1 closes the naming gaps)
but:

- The Phase 12 docs claim a `.yaao/.lock` that serializes `yaao_run` calls
  ([docs/phase-12/F12.1-mcp-server.md:54](../phase-12/F12.1-mcp-server.md#L54),
  [docs/phase-12/F12.4-run-plan-tool.md:76](../phase-12/F12.4-run-plan-tool.md#L76)).
  No such lock exists in `src/`. We need to either build it or drop the claim
  — we drop it, because the workflow we want is concurrent runs, not queued
  runs.
- There is no integration test that proves two concurrent runs against
  different feature branches actually work end-to-end. F16.1's unit tests
  cover naming; F16.2 covers the full lifecycle.
- The README and IMPLEMENTATION.md don't mention concurrent runs as a
  supported workflow. After this lands, they should.

## Scope

### Doc alignment

1. **Remove the `.yaao/.lock` claim from `docs/phase-12/F12.1-mcp-server.md`
   and `docs/phase-12/F12.4-run-plan-tool.md`.** Replace with a short
   "Concurrent invocations" section: `yaao serve` accepts overlapping
   `yaao_run` calls; isolation is per-runId on the filesystem and per-branch
   in git; merges to overlapping target branches surface as
   `task:merge-failed` via atomic ref CAS. No in-process serialization.
2. **Add a "Concurrent runs" subsection to the README** under
   `## Worktree orchestration` (or a new top-level section if that's
   cleaner). Cover:
   - The supported workflow: one `yaao run` per feature branch.
   - The invariants the engine gives you: worktree-path isolation by
     runId, branch isolation by `plan.featureBranch`, atomic merge-target
     CAS, no shared write to the user's checked-out branch (plumbing-based
     merge).
   - The two foot-guns: (a) two plans sharing `plan.name` *and* no
     `featureBranch` will collide on default task branches — set
     `featureBranch` or override `branch:` per task; (b) two runs auto-
     merging straight into `base-branch` (no `featureBranch` on either)
     can race, and the loser sees `task:merge-failed` — give each run its
     own `featureBranch`.
3. **Add an "Implementation notes" line to IMPLEMENTATION.md** under
   Phase 3 (worktree & git engine) and Phase 6 (merge engine) clarifying
   that the design supports cross-run concurrency. No new section — these
   are sentence-level annotations on existing phase summaries.

### Integration tests

The load-bearing one:

- `tests/phase-16/concurrent-runs/two-feature-branches.test.ts` — sets up
  a fixture repo with `main` checked out at root, two distinct execution
  plans (same shape, different `plan.name` and different
  `plan.featureBranch`), kicks both off via `Promise.all([runPlan(A),
  runPlan(B)])`, and asserts:
  - Both runs finish `status: 'success'`.
  - Each run's feature branch has exactly the merge commits expected from
    its tasks.
  - The other run's feature branch is unchanged by this run's work.
  - The root checkout (`main`) is unchanged on disk.
  - Both runs' journals exist under `.yaao/runs/<runId>/` with their own
    `runner.pid`, `journal.jsonl`, etc.

Supporting tests:

- `tests/phase-16/concurrent-runs/same-plan-two-features.test.ts` —
  reuses one plan file (post-F16.1 task branches namespace under
  `featureBranch`), runs it concurrently with `featureBranch: feature/a`
  and `featureBranch: feature/b` overrides via the `featureBranch` arg
  to `runPlan`. Asserts branch namespaces don't collide.
- `tests/phase-16/concurrent-runs/race-on-base-branch.test.ts` — two
  runs *intentionally* both auto-merging straight to `base-branch`
  (no feature branch). Asserts that one wins, the other emits
  `task:merge-failed`, the losing branch's work is preserved on its task
  branch, and neither run crashes. Documents the foot-gun.
- `tests/phase-16/concurrent-runs/journal-isolation.test.ts` — both
  journals are written without interleaving (each `journal.jsonl` is
  parseable and contains only its own run's events).

## Acceptance criteria

- All four integration tests pass.
- Every `.yaao/.lock` mention in the docs tree is either removed or
  replaced with the new concurrency-model text.
- README has a "Concurrent runs" section; IMPLEMENTATION.md notes that
  the worktree + merge engines support cross-run concurrency.
- F14.5's link-check (`tests/phase-14/docs/links.test.ts`, scheduled to
  land in Phase 14) catches no dangling references introduced by this
  edit.

## Out of scope

- Per-target merge advisory locks. See PHASE-16.md.
- Cross-process `.yaao/.lock`. Deliberately not building it.
- A `yaao runs --concurrent` flag or any new CLI surface. The workflow is
  "open two terminals, run two `yaao run`s" — no orchestration needed at
  the CLI layer.
- Backporting integration coverage to older phases. These tests are net-new
  under `tests/phase-16/` and the existing suite continues to cover its
  ground.
