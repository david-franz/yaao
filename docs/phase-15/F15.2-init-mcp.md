# F15.2 `yaao init --mcp` — auto-register yaao's MCP server

**Phase**: 14 — Release Polish
**Priority**: High
**Dependencies**: F1.4, F8.6, F12.1

## Goal

A new user goes from `npm i -g yaao` to "Claude Code / Cursor / Codex can call yaao tools" in a single command. Today the missing step is hand-editing the project's `.mcp.json` (Claude Code) and the per-agent equivalents — every other piece of plumbing (per-agent skill stubs, the MCP server itself) is already in place.

## Behaviour

`yaao init` defaults to writing yaao's own MCP server registration into the project's `.mcp.json`, alongside whatever else lives there. `--no-mcp` opts out. `--mcp` explicitly opts in (for users running `yaao init` against an already-initialised project who just want the MCP wiring).

What gets written:

```json
{
  "mcpServers": {
    "yaao": {
      "command": "yaao",
      "args": ["serve"]
    }
  }
}
```

If the file exists, merge under `mcpServers.yaao` — never replace siblings. If the existing `mcpServers.yaao` entry differs from what we'd write, leave it untouched and emit a warning ("found existing `yaao` MCP entry; not overwriting — run `yaao init --mcp --force` to replace").

## Per-agent files

The same MCP server registration also lands in:

- `.cursor/mcp.json` (Cursor's location)
- `~/.codex/config.toml` under `[mcp_servers.yaao]`
- Inline reference in `.github/copilot-instructions.md` (Copilot has weaker MCP coverage; the inline instruction is the fallback path described in F8.4)

F8.x emitters already handle three of these for *user* skills — F15.2 just teaches them to also emit a top-level yaao entry.

## Acceptance criteria

- `yaao init` in an empty repo produces a `.mcp.json` with a valid `yaao` entry; Claude Code opening that repo lists `yaao_*` tools without any further configuration.
- `yaao init` in a repo with a pre-existing `.mcp.json` containing other MCP servers preserves them.
- `yaao init --no-mcp` skips MCP registration entirely (parity with today's behaviour).
- A second `yaao init` in the same repo is a no-op for the MCP registration when the existing entry matches what we'd write.

## Tests

- `tests/phase-15/init-mcp/fresh.test.ts` — empty repo → valid `.mcp.json`.
- `tests/phase-15/init-mcp/merge.test.ts` — preserves existing `mcpServers.other`.
- `tests/phase-15/init-mcp/no-overwrite.test.ts` — non-matching existing `yaao` entry is left alone with a warning.
- `tests/phase-15/init-mcp/opt-out.test.ts` — `--no-mcp` writes nothing.

## Out of scope

- A `yaao init --mcp` flag that runs *outside* of `yaao init` (i.e. a standalone "wire MCP only" command). The whole point is that init does it by default; a standalone command would re-fragment the surface.
