# F15.5 Skill Refinement (Re-distillation)

**Phase**: 15 — Session → Skill Distillation
**Priority**: Medium
**Dependencies**: F15.1, F15.3, F15.4

## Goal

A skill's first version, distilled from a single session, will always be partial. Refinement is the path to making it *better* with reuse: re-run the distiller against an existing skill with a fresh session, merge what the new session reveals, and report the diff back to the caller so the calling agent can show it to the user before any write.

This is what turns "session → skill" from a one-shot extraction into a curated, growing library.

## Versioning is git's job

yaao does **not** auto-bump the `version` field in `skill.yaml` on refinement. The field exists in the F8.1 schema (`z.number().int().positive()`) and is set to `1` on initial creation by the distiller; refinement preserves whatever value is currently there. If the user wants to bump it manually they can — yaao won't touch it.

The audit trail lives in git. `.yaao/skills/` is tracked by the project repo, so `git log -p .yaao/skills/<name>/` is the canonical history with diffs, dates, and commit messages. yaao does not maintain a parallel backup directory or numbered version files — that would be reinventing version control inside a directory git already watches, and would create a "which is the source of truth?" ambiguity.

One small UX concession: yaao checks whether `.yaao/skills/<name>/` has uncommitted changes before overwriting. If it does, the call returns `ok: false` with `YAAO_SKILL_DIRTY` and the calling agent is expected to surface that to the user (typically asking "the skill directory has uncommitted changes — overwrite?"). The agent re-calls with `force: true` to proceed. See "Pre-refine uncommitted-changes check" below.

## Invocation

```json
{ "name": "yaao_distill", "arguments": { "refine": "add-api-endpoint", "session": { ... } } }
```

The session payload is the same `SessionRecord` shape used for initial distillation (F15.2). The difference from initial creation is the distiller's prompt mode and the emission's overwrite semantics.

## Distiller Mode: Merge

When `existing` is supplied to the distiller (F15.1), Stage 3 of the prompt changes:

- Load the existing `skill.yaml` + `prompt.md` (and its "Distillation notes" tail).
- Run Stage 1 + 2 on the *new* session in the usual way, producing a fresh `Keep` / `Drop` analysis.
- Stage 3 becomes a **merge**, not an emit:
  - **Conventions**: union of existing + new — but see "Detecting contradictions" below for the concrete conflict signal.
  - **Procedure**: prefer the existing structure; insert new steps where the new session reveals gaps. Update step wording only if the new session's wording is clearly more general.
  - **Anti-patterns**: union; never remove an existing anti-pattern (the user wrote that for a reason).
  - **Inputs**: union; for shared input names, take the more permissive default.
  - **Distillation notes**: append the new session's notes under a `### Session N (YYYY-MM-DD)` heading. Existing notes are preserved verbatim.

The distiller emits the merged `skill.yaml` + `prompt.md` and a third artifact:

- **`---changelog---`** — a fenced block listing what changed relative to the previous version, in human-readable form. Surfaced in the MCP response so the calling agent can present it to the user.

## Detecting contradictions (the load-bearing rule)

Generic "does the new convention contradict an existing one" is an open NLP problem dressed as a structural one — running fuzzy match over two natural-language bullet lists either flags everything or nothing. v1 ships with a tighter, **structural** signal that's tractable and useful even if it's not exhaustive:

A new convention bullet is flagged as conflicting with an existing one when **all three** hold:

1. They share a **subject token** — a backtick-quoted identifier appearing in both bullets (e.g. `` `src/api/` ``, `` `ApiResponse<T>` ``, `` `cmd_meminfo` ``). The token is the load-bearing identifier the conventions are *about*.
2. The bullets differ in their **assertion** (everything outside backticks). String inequality of the non-token text is enough — the distiller's prompt is responsible for producing tight bullets, so noise like "in this codebase" doesn't dominate the diff.
3. The bullets are in the same **section** of `prompt.md` (e.g. both under `## Conventions in this codebase`).

This is **advisory**: it catches the common case (path conventions, type-name conventions, command-name conventions — all natural to write as backtick-quoted in our skill format) and misses the edge case (two prose paragraphs saying contradictory things with no shared identifier). Misses surface as silent merges into the union; the user catches them on review via the diff that `apply: false` returns.

Conventions without backtick tokens are unioned without conflict detection. The distiller prompt explicitly tells the agent to **prefer backtick-quoted identifiers when writing convention bullets** — that's the rule that makes the structural check useful. Failing that, conflicts surface in the diff but not in the structured `conflicts[]` array.

The reviewer's example — "endpoints now live in `src/routes/` not `src/api/`" — works because both the existing and new bullet would mention one of those paths as a backticked identifier. The structural check fires; the user sees an explicit conflict line in the MCP response.

A future v2 may add LLM-driven semantic conflict detection (run the agent over both bullet lists and ask). Not in v1; structural rule first.

## No-op Detection

A refinement that yields no changes (the new session contained no new signal) is detected and skipped — no write, no diff. v1 uses a **structural check** rather than relying on the agent to self-report:

After Stage 3 emits the merged `skill.yaml` + `prompt.md`, the emission pipeline (F15.3) compares them byte-for-byte against the existing files. If both are identical, the merge is a no-op:

```json
{ "ok": true, "skill": null, "noop": true, "reason": "session adds nothing new to add-api-endpoint" }
```

The structural check is preferable to an agent-instruction-based detection because the agent self-reporting "I didn't change anything" is exactly the kind of thing models hallucinate when they're tired. Byte equality is deterministic and free.

This matters because re-distilling against minor or off-topic sessions is the most common usage pattern; silent no-ops keep that cheap.

## Pre-refine Uncommitted-Changes Check

Before any write, yaao checks `git status .yaao/skills/<name>/` (project scope; user scope is skipped — `~/.yaao/skills/` may not be in any repo). If the directory has uncommitted changes and `force: false`:

```json
{
  "ok": false,
  "error": { "code": "YAAO_SKILL_DIRTY", "message": "skill directory has uncommitted changes" },
  "dirty": { "modified": ["skill.yaml"], "untracked": ["examples/foo.md"] }
}
```

The calling agent is expected to surface this to the user — typically by reporting the dirty files and asking whether to overwrite. The agent then re-calls `yaao_distill` with the same arguments plus `force: true` to proceed. This delegates the human-in-the-loop confirmation to the agent's natural-language surface rather than reinventing a TTY prompt inside yaao.

The check uses the existing git wrapper (F3.3) — no new dependency.

## Diff and Conflict Reporting

When the refinement is non-trivial (not a no-op) and the directory is clean (or `force: true`), yaao computes a unified diff of the existing skill vs. the merged version and includes it alongside the distiller's changelog in the MCP response. Two paths:

**Auto-apply path** (no conflicts, `apply: true` default):

- yaao writes the merged skill atomically (F15.3) and returns the diff + changelog as part of the success payload.
- This is the common case — the calling agent typically wants the change applied and reported.

**Preview path** (`apply: false`):

- yaao does **not** write. It returns the merged `skill.yaml` + `prompt.md` content plus the diff and changelog. The calling agent can show this to the user, get confirmation, and re-call with `apply: true` to commit.

**Conflict path** (the merge flagged at least one convention conflict):

- yaao does **not** auto-apply regardless of `apply`. It returns `ok: false` with `conflicts: [...]` describing what contradicts. The agent surfaces conflicts to the user, who decides which convention is canonical and re-calls with an adjusted session (or accepts the new direction by passing `resolveConflicts: 'prefer-new'`, etc. — see Schema below).

This is the right default because contradictions are usually signal that the codebase actually changed direction, and the user should make the explicit call about which version of the convention is canonical.

## Schema additions (on `yaao_distill`)

F15.4's schema gains two refinement-specific inputs:

- `apply` (boolean, default `true`) — when `false`, return the merged content and diff without writing. Preview mode.
- `resolveConflicts` (`'manual' | 'prefer-existing' | 'prefer-new'`, default `'manual'`) — how to resolve flagged contradictions. `'manual'` blocks auto-apply and returns `conflicts: [...]`; the other two are explicit overrides for cases where the user has already made the decision.

`force` (already in F15.4's schema) overrides the `YAAO_SKILL_DIRTY` check.

## Emission Routing

`EmissionRequest.merge = true` (set by F15.4 when `refine` is in the call) tells F15.3 to:

- Skip the `YAAO_SKILL_EXISTS` check.
- Take the file lock on the target directory before any write.
- Atomically rename the new files into place, replacing the existing pair.
- Re-trigger `skills install` (per F8.6) so per-agent stubs reflect the new content.

The previous version is **not** backed up by yaao — git is the history. See "Versioning is git's job" above.

## Output (apply path)

```json
{
  "ok": true,
  "skill": {
    "name": "add-api-endpoint",
    "dir": ".yaao/skills/add-api-endpoint",
    "scope": "project"
  },
  "changelog": [
    { "type": "procedure", "summary": "added step 4 (lint:api)" },
    { "type": "convention", "summary": "ApiResponse<T> wrapper" }
  ],
  "diff": "<unified diff of skill.yaml + prompt.md>",
  "conflicts": [],
  "gitHistory": "git log -p .yaao/skills/add-api-endpoint/"
}
```

The MCP `content[]` carries a human-readable summary (changelog as bullets, plus a pointer to `git log` for full history) that the calling agent can show the user verbatim.

## Acceptance Criteria

- Re-distilling an existing skill with a session that introduces a new convention produces a merged skill with the new convention added (and the MCP response includes a diff and changelog).
- The merged skill's `version` field is left at whatever the existing skill had (yaao does not auto-bump).
- A session that introduces nothing new returns `{ ok: true, noop: true }` with no write.
- A session that contradicts an existing convention returns `ok: false` with structured `conflicts: [...]` and does not write.
- `resolveConflicts: 'prefer-new'` applies the new direction; `'prefer-existing'` keeps the old. Default `'manual'` blocks auto-apply.
- The previous version's anti-patterns and distillation notes are preserved verbatim in the merged output.
- `apply: false` returns the merged content + diff without writing; a follow-up call with `apply: true` writes it.
- Refining a skill directory with uncommitted changes returns `YAAO_SKILL_DIRTY` and does not write; `force: true` overrides.
- After refinement, `yaao serve`'s watcher reissues `tools/list_changed` so connected clients pick up the new content.
